# CAD 実形状（URDF）でロボットを動かす

ビューアの機体は **`cad/urdf/tr.urdf` そのもの**を読んで、試合シムの状態で
12 個の関節を全部動かしている。簡略形状（`src/render/robot-mesh.ts`）は
読み込みが終わるまでのつなぎで、設定 → 表示 →「機体をCAD実形状で描く」で
いつでも戻せる。

## 手順

```bash
cd cad
.venv/bin/python scripts/export_meshes.py   # 材質ごとの STL (mm)
.venv/bin/python urdf/tr_urdf.py            # tr.urdf

cd ../viewer
npm run urdf:shape    # 当たり判定と LiDAR 取付 → src/config/robot-shape.ts
npm run urdf:check    # 全関節が試合中に動き、可動域を超えないか + 寸法 30 項目
npm run lidar:check   # 実機の取付で点群と自己位置推定が成立するか
npm run dev           # /urdf/** は cad/urdf/ から直に配る（同期不要）
```

⚠ **CAD を直したら 2 つとも回す。** メッシュだけ・URDF だけ更新すると、
形と関節の原点が食い違ったまま動く（見た目は破綻しないので気づきにくい）。

### 開発中は `public/` を経由しない

⚠ **`public/urdf/` に置くと、サーバ起動より後に増えたファイルが
`index.html` に化ける。** Vite は起動時に public のファイル一覧を作って
持つので、あとから増えたファイルは「public に無い」と判定され、
SPA フォールバックで **HTML が 200 で返る**。STL パーサはそれを
バイナリ STL と信じて三角形数 17 億個を確保しようとし、
`Invalid typed array length` という原因の見当も付かない例外で落ちる。

実際に踏んだ: サーバ起動 05:38 / メッシュ生成 05:49 → 58 枚中 **56 枚**が
HTML（残る 2 枚は名前がアルファベット順で先頭の、コピーが間に合ったもの）。

「同期したらサーバを再起動する」で運用するのは忘れた方が負けるので、
`vite.config.ts` の `urdfDev` プラグインが開発時だけ `/urdf/**` を
`cad/urdf/` から**毎リクエスト読んで**返す。無いパスは 404 を返す
（index.html にフォールバックさせない）。

本番ビルドは dist に入れる必要があるので `npm run build` が
`urdf:sync` を先に呼んで `public/urdf/` へ複製する。

⚠ ローダ側でも守っている: 返ってきた中身が HTML/XML だったり、
STL のヘッダと長さの辻褄が合わなければ、**どの URL が何を返したか**を
言って落ちる（`urdf.ts: fetchMesh`）。

## 動かしている関節（12 個 = 実機のモーター/サーボと 1 対 1）

| 関節 | 型 | 駆動 | 何が動かすか |
|---|---|---|---|
| `wheel_fl/fr/rl/rr` | continuous | M3508 ×4 | メカナム逆運動学（`sim/mecanum.ts`）の積算角 |
| `turret_yaw` | revolute ±30° | M3508 | 照準（`turretYaw`）。届かないぶんは車体が回る |
| `shooter_pitch` | revolute 20〜70° | M2006 + ウォーム | 弾道解（`aim.angleRad`） |
| `roller_upper/lower` | continuous | M3508 ×2 | `rollerRpm` の積分。⚠ 上下で符号が逆 |
| `singulator` | continuous | M2006 | 送給中（`anim.feed ≥ 0`）だけ回る |
| `grabber_slide` | prismatic 0〜316mm | M3508 + ベルト | 一括ピックアップの前後 |
| `grabber_press` | prismatic 0〜138mm | サーボ | 上押さえ |
| `fork_tilt` | revolute 0〜22° | サーボ | フォークの傾き |

対応づけは **`src/render/urdf-joints.ts`** に置いてある。Three.js に依存
しないので、ブラウザ抜きで `npm run urdf:check` から呼べる。

⚠ **描画コードの中に埋めないこと。** ここが「どのモーターをどう回すか」の
仕様そのもので、実機の `cad/control/tr_control.py` と突き合わせる相手になる。

## 色は CAD の材質から来る

⚠ **STL は色を持てない。** 1 リンク 1 枚で書き出すと、アルミもモーターも
プラダンも同じ灰色になる。`export_meshes.py` は**材質ごとに STL を分けて**
書き出し、割付を `meshes/materials.json` に残す。`tr_urdf.py` はそれを読んで
1 リンクに複数の `<visual>`（それぞれ `<color rgba>`）を出す。

* 色 … `cad/src/tr_lib.py` の `MAT_COLOR`（**唯一の情報源**）
* 質感 … `viewer/src/render/urdf-robot.ts` の `FINISH`（金属かどうか・つや）

⚠ **ビューア側で色を持たない。** 持つと、CAD で材質を変えたのに画面だけ
前の色、が起きる。ビューアが決めてよいのは metalness / roughness だけ。

チーム色は機体を塗りつぶさず、地の色にごく薄く寄せるだけにしてある
（青 0.88,0.93,1.0 / 赤 1.0,0.90,0.88）。材質の見分けを潰さないため。

base_link は 25 材質・全リンクで 55 枚の STL に分かれる（合計サイズは
1 枚のときと同じ 21MB）。

⚠ **材質で分けるとき、葉を裸で取り出してはいけない。** build123d の
`location` は親から見た相対値で、`Pos(0, y, 0) * Rot(90, 0, 0) * roller()`
のように**親側に回転が乗っている**部品がある。木を降りて葉だけ別の Compound に
詰め直すと、その回転が消えて**部品の向きが変わる**。

実際に踏んだ: 射出ローラーが軸を縦にして書き出され（`link_roller()` の
bbox 90×602×90 が、詰め直すと 90×602×**44.2**）、Y 軸まわりに回るはずの
ローラーが画面では首を振っていた。**関節の符号は正しかった**——
`shooter_pitch` 座標で測ると上下とも接触点は +X（射出方向）へ 8.94mm 動く。
慣性と当たり判定は `link_roller()` から直に作るので正しく、**見た目だけ**が
壊れていた。1 リンク 1 枚だった頃は木を降りないので起きなかった。

`export_meshes.py` は祖先の姿勢を掛けてから葉を返し（`_leaves`）、
さらに**詰め直した bbox が元と一致するか**をリンクごとに照合して、
ずれたら書き出さずに落ちる。

## 可動域は CAD が決める

`src/config/params.ts` の `turret.yawLimit / pitchMin / pitchMax` と
`wheel.r / k` は **CAD から来た数字**で、勝手に広げてはいけない。

| 値 | 出どころ |
|---|---|
| `turret.yawLimit = 0.523599` (±30°) | `tr.urdf: turret_yaw` / `tr_control.py: YAW_LIMIT` |
| `turret.pitchMin/Max = 0.349066 / 1.22173` | `tr.urdf: shooter_pitch` / `tr_control.py: PITCH_MIN/MAX` |
| `turret.muzzleY = 1.0` | `tr_params.py: NIP_Z = 1000mm` |
| `wheel.r = 0.05` (φ100) | `tr_params.py: WHEEL_DIA` / `tr_control.py: WHEEL_R` |
| `wheel.k = 0.3` (LX=LY=0.30) | `tr.urdf` の車輪取付 / `tr_control.py: LX, LY` |
| `field.ROBOT.*`（後端 421 / 歯先 364.4〜680.4 / 歯上面 763） | `tr_params.py` |

⚠ ここがずれていた実例（2026-08-03 に直した）:

* 砲塔ヨーがシムでは **±137°** まで回れた。15 試合を通すと最悪 **−56°** の
  指令が出ていて、実機（±30°）では絶対に出せない角度で命中させていた。
  → 可動域を CAD に合わせ、足りないぶんは**車体を回して**埋めるようにした
  （`MatchSim.aimWithBase`）。実機で必ずやる操作でもある。
* 車輪半径が **φ127** のままだった（実機は φ100）。接地速度に対して 21%
  遅く回るので、走っているのにタイヤが滑って見える。
* 砲口が **1.5m** だった。CAD の `NIP_Z` は 1000mm（900 では仰角ユニットが
  台座を貫くので上げた経緯がコメントに残っている）。500mm 高い所から
  撃っていたので、旗（3.0m）への必要初速を実機より低く見ていた。
  ⚠ 実機制御 `tr_control.py` の `NIP` は **900mm のまま**残っていた
  （CAD が却下した高さ）。こちらも 1000 に直した。

## 雑巾回収の向きと位置

⚠ **フォークは車体の後ろ（-X）**、砲塔は前（+X）。だから補充では
**机に背を向ける**。シムは「側面グラバーだから車体旋回ゼロ」と書いて
攻撃方位のまま机に正対していたが、それだと砲塔を机に突っ込んでいる。

| | 値 | 根拠 |
|---|---|---|
| 機体 z（青） | 1.751 | 机の縁 1.300 + 後端 0.421 + すきま 0.030 |
| 向き | 青 0° / 赤 180° | フォーク（-X）が机を向く |
| 車体後端 | 1.330 | 机の縁より 30mm 手前 |
| 歯先（全閉） | 1.387 | 縁より手前＝寄せるとき天板を叩かない |
| 歯先（全開） | 1.071 | 机中央 1.075 に届く＝山の向こう側に歯が入る |

⚠ **円の当たり判定だと 79mm 足りなかった。** 機体を円（r=0.5）で見ていた
ので、どう向けても机から 0.5m 離れる。実際に効くのは後端 421mm。
正対しているときだけ実効半径を 0.421 に落とす（`ROBOT_HALF_LEN`）。
これが無いと歯先が 1.140 で止まり、山の手前 65mm で掬えない。

寄せはクリープ 0.1m/s（`CREEP_SPEED`、机まで 150mm から）。
strategy.md §位置決めと `tr_control.py: CREEP` と同じ。

グラバーの工程の切れ目も**モーターの速度で決まる**（`urdf-joints.ts`）:
伸ばし 1.05s（316mm ÷ 0.3m/s）→ 押さえ 1.38s（138mm ÷ 0.1m/s）→
傾け 0.19s（0.384rad ÷ 2rad/s）→ 引込 1.05s。合計 3.7s が機構の下限で、
残りは押さえたままの整定に配る。⚠ 前は 0.3/0.5/0.75 という割合だったので、
いちばん遅い上押さえが一瞬で降りていた。

## LiDAR は URDF の実体で当てる

⚠ **相手機を「0.76m 角の正方形」で近似しない。** 断面はスキャン面で違う。
`src/config/robot-shape.ts`（**生成物**・`npm run urdf:shape`）が URDF の
`<collision>` を全部持っていて、`sectionRects(h)` が高さ h で切る。

| 走査面 | 断面 | 見えるもの |
|---|---|---|
| 0.112 m（下段） | 3 枚・**0.722 × 0.970 m** | 底板 0.842×0.722 の前後に LiDAR の胴が出る |
| 0.500 m（上段） | 4 枚・0.743 × 0.788 m | 側面トラスの**厚さ 24mm の板 2 枚**＋砲塔台＋上段 LiDAR。中は素通し |

正方形で塞いでいた頃は、上段で相手越しの物が全部消えていた。

### 走査原点も車体中心ではない

取付は URDF の **fixed 関節**（`lidar_low_front` / `lidar_low_rear` /
`lidar_high`）が唯一の情報源。CAD の `tr_params.py` から出している。

| センサー | 局所 (X左, Y上, Z前) | 方位 |
|---|---|---|
| `lidar_low_front` | (0, 0.112, +0.454) | 0° |
| `lidar_low_rear` | (0, 0.112, −0.454) | 180° |
| `lidar_high` | (0.350, 0.500, 0.427) | 0° |

⚠ 前後の下段は **908mm 離れている**。中心 1 点から飛ばすと、実機なら片方から
しか見えない物（机の脚・椅子の脚）が両方から見えて、ICP が実機より当たる。
⚠ 走査面は **0.112m**（0.12 ではない）。0.12 だと胴が椅子の座面と 8,562mm³
重なるので CAD が下げた経緯がある。
⚠ `scanToLocalPoints()` は取付ぶんの**平行移動を必ず足す**。落とすと前後の
点群が 0.9m ずれて重なり、ICP が別の場所に収束する。

### リトライ中はセンサーを焚かない

人が持ち上げてスタートゾーンへ運ぶ区間は機体が非常停止中で、計測輪も LiDAR も
電源が無い。それでも ICP を回していたので、オドメトリ 0 のまま地図に引っぱられて
**推定が 6m 流れていた**（60s×6 通りのうち 4 通りで発生）。復旧完了時に既知の
スタートゾーン座標で reset するのが実機の手順で、その間は素直に止める。

## 移動バケツの位置

⚠ **車体中心ではない。** CAD は `BUCKET_X = -70mm` / `y = 0`、マスト上端に座る。

| | 値 | 出どころ |
|---|---|---|
| 局所 (X, Z) | (0, −0.070) | `tr_assembly.BUCKET_X` |
| 上面 | 1.430 m | `BUCKET_SEAT_Z 1175 + BUCKET_H 255`（規定 3.2.3b の 1200..2100 内）|
| φ | 273 mm | エンテック PO-24A |

ビューアは (0.24, −0.24) と**斜め後ろ**に置き、既定の高さも青 2.0 / 赤 1.5 に
していた。CAD 実形状で描くと、画面のバケツと当たり判定が横 340mm・高さ 570mm
食い違い、狙った弾がバケツの脇を素通りしていた。`ROBOT.bucket` が唯一の情報源。

`bucketTopY` は規定の範囲で上げ下げできる作戦の値だが、**既定は CAD が建てた
高さ**にする。⚠ CAD 実形状で描いているときは、値を変えても画面のバケツは
1.430m のまま（メッシュに焼き込まれている）。

## 検査

`npm run urdf:check` は相手 3 型 × 自陣 5 戦略 = **15 試合**を 1/60 s で
回し、両陣の全関節の最小・最大を取る。落ちるのは

* URDF に無い関節を動かしている / URDF にあるのに動かしていない
* 試合を通して一度も動かない関節がある（＝そのモーターは制御していない）
* revolute / prismatic が URDF の lower..upper を出る

⚠ **1 試合では足りない。** 砲塔の振り方は相手の型で変わる。上の −56° は
`blocker/standard` でしか出なかった。

寸法の照合（30 項目）には `robot-shape.ts` が URDF と一致しているかも入れて
ある。**URDF は生成物で git に入らない**ので、ここで見ないと表だけが古くなる。

`npm run lidar:check` は 60s × 6 通りを**非 headless**で回して、点群と自己位置
推定を見る。⚠ `urdf:check` は headless なのでセンサーを 1 度も焚かない。
落ちる条件は「推定が真値から離れる（RMS > 0.15m / 最大 > 0.40m）」
「点群が返ってこない」「相手機を検出できない」。
実測 RMS 0.009〜0.010m / 最大 0.061〜0.085m。

`?capture=1` を付けたときだけ `preserveDrawingBuffer` を有効にしてある。

```bash
# 例: ヘッドレスで 1 枚撮る
python - <<'PY'
# playwright で http://127.0.0.1:5177/?capture=1 を開き、
# window.SIM.urdfStatus().ready を待って canvas.toDataURL() を保存する
PY
```
