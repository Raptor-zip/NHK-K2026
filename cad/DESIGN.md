## 0. 戦略書からの設計変更（重要・先に読むこと）

`strategy.md` §3/§4.7 は「移動バケツ上面 ≈2000mm・砲口高 ≈1500mm」を前提にしていた。
本設計はこれを **バケツ上面 1407mm・射出点 900mm** に変更した。理由は規定の連鎖:

1. **3.2.2**「スタート時 高さ 1200mm 以内」。4.1.3 でもスタンバイ時 1200mm 以内が明記される。
2. **3.2.3c**「ロボット・マスコット・保持中の雑巾のいかなる部分も、バケツの 2L 目盛りより
   上に出られない」。バケツ底を高くしない限り、機体の全高が 2L 目盛りに縛られる。
3. **FAQ 3.2 Q2**「ロボットの足回りの動きとは関係なく、独立して移動バケツを動かすことは
   認められません」。→ 競技開始後にマストを伸ばしてバケツを 2000mm へ上げる展開機構は、
   **規定違反と判定されるリスクがある**（3.2.2 の「可動部を展開して1800mm」との整合が
   グレー）。

→ **バケツを展開しない固定高さにする**と、上の3つが同時に満たせる。設計値は
バケツ底 1153 / 上面 1407（規定 1200〜2100 ✓）、2L 目盛り ≈1218、機体最高点 1152（＜1218 ✓）。
展開機構ゼロなので軽く・剛性が高く・故障要因が1つ減る。

失うのは「高いバケツで相手に急角度の投入を強いる」防御優位のみ。これは §2.4 の
「射撃中も車体微動」で補う。

**弾道の代償は小さい**（射出点が 1500→900 に下がっても届く）:

| 目標 | 水平距離 | 必要上昇 | 仰角60°で必要な初速（真空近似） |
|---|---|---|---|
| 旗 横棒 3000mm | 3.0m | 2.10m | **7.6 m/s** |
| 旗 横棒 3000mm（仰角45°） | 3.0m | 2.10m | 9.9 m/s |

設計射出速度域 7〜15 m/s の内側。空気抵抗込みでも `gpusim` の実測較正で吸収できる。

> **要ルール質問（8/24まで）**: 「競技開始後にマストを伸長して移動バケツの高さを変えることは
> FAQ 3.2 Q2 の『独立して動かす』に該当するか」。回答が「該当しない」なら、本設計に
> 昇降ステージ（M2006＋ボールねじ、ストローク約600mm、+1.5kg）を追加してバケツ2000mm案へ
> 戻せる。`tr_params.py` の `MAST_TOP_Z` / `NIP_Z` を変えるだけで全体が追従する構造にしてある。

もう一点の変更: **砲塔ヨーを ±135° → ±30°** に限定した。粗照準は車体ヨー（メカナム）で作り、
砲塔は「車体運動の打ち消し・微調整」に徹する。これにより **ホッパー・シンギュレータ・斜路を
車体固定にでき**（旋回体に載せると装填のたびに砲塔を後ろへ向ける必要がある）、供給経路が
ヨー角に依存しなくなる。モーター構成は §4.0 の11軸とちょうど一致する。

## 1. 座標系と全体レイアウト

* 原点 = 床面上・メカナム4輪の接地中心
* **+X = 前方（射出方向・砲塔ヨー0°）** / **-X = 補充スポット（机）方向・グラバー伸長方向** / +Y = 左 / +Z = 上
* 単位 mm

```
        z                    ┌── 移動バケツ φ273×H255（底1153 / 上面1407 / 2L目盛≈1218）
  1407 ─┤        ┌───────────┴────────────┐
  1153 ─┤   ┌────┤ バケツ受け板 t2 + 片持ちビーム
  1152 ─┤   │ ← 機体最高点（2L目盛りより下）
   900 ─┤   │              ●射出点（ニップ＝ヨー軸＝仰角軸の交点, X=+235）
   838 ─┤   ├──────────────────────────┤ 側面トラス上桁 / 砲塔台座
   800 ─┤   │   ══ スライドレール SRX3616（|Y|=350）
   763 ─┤   │   ── 櫛歯上面（下面761 = 机上面760 + 1mm）
   712 ─┤   ├── ホッパー開口（X=-435..-15, Y=±310・机天板の下へ潜れる高さ）
   700 ─┤   │   ／斜路45°→ニップ
   135 ─┤   └───────────────┤ ベースフレーム上面
   115 ─┤   ┌───────────────┤ ベースフレーム下面
    50 ─┤   ● メカナム車軸（φ100）
     0 ─┴───────────────────────────────── 床
        -435            0            +466
```

**「射出点＝ヨー軸＝仰角軸」を1点に集める**のが本設計の核。砲塔をどう振っても射出点が
動かないので、弾道テーブルが「射出点の絶対座標＋方位＋仰角＋速度」の4変数で閉じる。
自己位置推定（LiDAR）の誤差がそのまま照準誤差になるだけで、機構由来の項が消える。

## 3. サブシステム設計

### 3.1 走行系（M3508 P19 ×4 / メカナム φ100）

| 項目 | 値 | 根拠 |
|---|---|---|
| ホイール | メカナム φ100 × 幅50、9ローラー | φ127から変更し −1.0kg。ロンリウム＋50mm幅ビニールテープの継ぎ目は問題なく越えられる |
| トレッド × ホイールベース | 600 × 600 | 正方配置でメカナムの逆運動学が最も単純 |
| 車軸高さ | 50 | フレーム下面115 → 最低地上高115mm |
| 推力 | 4 × 3.0N·m ÷ 0.05m = **240N** | 35kg で加速度 6.8m/s²（実運用は電流バジェットで 1.5〜2.0 に制限） |
| 最高速 | 482rpm × π × 0.1 = **2.52 m/s** | シム計画の要求（約2m/s）を満たす |
| 転倒余裕 | 重心高 385mm / トレッド 600 → 傾斜 38° | 急制動でも余裕 |
| 取付 | CNC切削 A5052 t5 の縦板（φ26インロー座＋4-M4 PCD35）+ 上部耳 t4 でフレームへ | M3508 データシート p.4 の実寸法 |

### 3.3 砲塔（ヨー ±30°）

* 旋回支持: φ220 Vリング + カムフォロア3個（クロスローラリングより安価・軽量）
* 駆動: M3508 P19 + HTD5M 20T→60T（3:1）→ 出力 9.0 N·m / 160rpm
* 砲塔慣性 J ≈ 0.31 kg·m²（砲塔＋仰角ユニット＋ローラー 4.94kg、慣性半径 0.25m）
  → 角加速度 29 rad/s²。ジャイロで車体ヨーを打ち消すのに十分な帯域
* 台座: 側面トラス上桁に渡した HFS5-2020 横梁2本 + A5052 t4 リングプレート

**装填シーケンス**（グラバーは車体後面なので、攻撃方位のまま後退で机へ寄れる。旋回不要）:

1. LiDAR自己位置で机正面150mmへ定型後退 → 前面ToF×2 で平行度 ±2° に合わせる
2. フォークを 0.1m/s で挿入（根元リミットSWが抵抗を検知したら即後退＝机を押す事故の防止）
3. 上押さえ下降 → 山ごと引込（375mm）→ 押さえ解放 → 最終50mmで固定カムが櫛歯を22°傾け、山が自重でホッパーへ滑落（`fork_tilt`：モーターなしの受動関節）
4. 教壇へ前進しながら、ピックローラーが1枚分離 → 斜路 → ニップへ（到着後1秒で初弾）

### 3.5 マスト・移動バケツ

* 主柱は**側面トラスの後柱をそのまま z=1150 まで延長**（部材3役兼用で −0.9kg）
* 上部横梁（Y方向780）+ 片持ちビーム2本（X方向300, |Y|=150）でバケツを X=-70 に保持
* バケツ受け A5052 **t3**（受け円環 φ186/φ236 + ビームに載る帯2本。丸穴の肉抜きは廃止）
* バケツは**底面 4-M5 で受け板に留める**（規定 3.2.3c は 2L 目盛りより「上」の加工を
  禁じている＝下は可）。バケツの中には皿頭を沈める押さえリング PETG t4
  （規定 3.2.3d「固定のみを目的とした部品」）。胴は位置決めタブ PETG 4 個で
  16mm ぶん抱える → §44
* 片持ちたわみ: 1.5kg × 390mm、2本の2020（I=1.48e4 mm⁴）で δ=0.29mm ✓
* 射出経路（X>235, z>900）に構造物が一切入らないよう、上部梁は全て X<+145 に収めた

### 3.6 椅子・マスコット

#### 5.2.1 LiDAR のレベリング座（4点調整）

**2D LiDAR は走査面が水平でないと使えない。** 走査面が θ 傾くと、距離 L の
点は L·sinθ だけ上下にずれる:

| 傾き | 1m先 | 3m先 | 5m先 |
|---|---|---|---|
| 0.2° | 3.5mm | 10mm | 17mm |
| 0.5° | 8.7mm | 26mm | 44mm |
| 1.0° | 17mm | 52mm | 87mm |

下段（走査面 112）は 1° 傾くと 5m 先で光が床（0）に潜るか、机の天板（700）
より上へ抜ける。**壁として使えるはずの点が消え、消えていることに気づけない**
（ICP は残った点だけで平気で収束する）。停止精度の目標は ±20mm なので、
取付の傾きは **0.2° 以下**に追い込みたい。ところが切削と組立の公差だけでは
0.5〜1° 残るうえ、**残った傾きは図面からは分からない**（実測して直すしかない）。

→ 3 台とも、立板と本体のあいだに **2 枚板 + 4 点**のレベリング座を入れた。

```
       ○ 調整ねじ M4×30（頭は**いちばん上**・上から回す）
   ┌──────────────────────────┐  ← 固定板 t6（ばかっ穴 4・横材の上面へ 2-M5）
   │   ばね            ばね   │     すきま 12mm（=調整代 ±3mm）
   ├──────────────────────────┤  ← 可動板 t6（M4 タップ 4・中央 φ40）
   │  UST-20LX 50×50×70       │  ← **下向きに吊る**（底面 2-M3 ピッチ40）
   │      検出面 ────────────  │     取付面から 47.4mm 下
   └──────────────────────────┘
```

* 調整ねじ **M4×30 ×4** + 圧縮ばね φ8×20（k=1.2N/mm・中立で 4 本合計 38N＝
  LiDAR 130g の 30 倍）。締めればその隅が下がり、緩めればばねが押し上げる
* すきまは**ばねの密着高さ 8.8mm** から決めた。いちばん締めた隅（12−3=9mm）で
  密着すると、そこから先はばねではなく板が突っ張る ＝ 調整代が名目だけになる
* ねじ間隔 44×68mm。**LiDAR の胴 50 角の外**に出してある
* 分解能は **1/12 回転（時計の 1 時ぶん）で 0.076°**。M4 のピッチ 0.7mm を
  短辺 44mm で割った値で、目標の 0.2° は指で回せる粒度に収まる
* 調整後は固定板の下に出たねじ先を **M4 ナットで固締め**して戻り止めにする
* 板の中央は **φ40 で抜いてある**。上段の配線はここを真下から通す
  （板の外を回すと、傾けたとき配線が突っ張って傾きを戻す向きに効く）

**直すのはロールとピッチだけ。** ヨー（走査の 0° 方向）と XY は
可動板のばかっ穴のがた（±0.5mm ＝ 68mm スパンで 0.4°）ぶん残るが、これは
**外部パラメータの校正で吸収する**種類の誤差で、機構で追う必要はない
（走査面の傾きと違って、点群を回せば消える）。面内はばね荷重 38N ×
μ0.2 ＝ 7.6N の摩擦で保つ。LiDAR 130g が 2G で振られても 2.6N なので動かない。

**位置を決めているのはばねではなく、ねじの頭。** ばねは可動板を頭へ押し付ける
予圧でしかない（4 本合計 38N ÷ 可動部 0.18kg ＝ **21G まで浮かない**）。
ここを取り違えて「ばねで支える」設計にすると、走行の振動で走査面が揺れる。

追い込んだ 0.2° が走行中も保つか（片持ちのたわみ）:

| 経路 | 断面 | 先端荷重 3.4N での傾き |
|---|---|---|
| 固定板の張り出し 37mm | 70×t6 | 0.0015° |
| 立板の垂れ 69mm | 70×t8 | 0.0024° |

合計 0.004° で、追い込む粒度（0.076°）の 1/19。**機構のほうが測定より硬い**
ので、調整した値がそのまま残る。

⚠ **固定は「接触必須ではない」宣言（`ADJUST`）にした。** 2 枚の板のあいだは
*空いているのが正しい*（すきまが調整代そのもの）。`BOLT` で宣言すると
`assembly_check` の「宣言した固定先と接していない」に必ず落ちるし、
接するように描くと調整代が 0 ＝ 機構が無いのと同じになる。

⚠ **同時に、前の取付が実物にならないことも直した。** 前は立板（t3）の側面に
φ60 の胴を抱かせて「4-M3 で留めた」と宣言していたが、円筒の側面と平板は
**線でしか当たらない**（座面 0mm²）。しかもその向きだと走査面は**垂直**になる。
LiDAR は底面フランジで水平面に留めるものなので、受けは水平でなければならない。

⚠ **取付は「上に載せる」ではなく「下向きに吊る」。** 実機の写真（フレームの
上に板、その下にセンサー）と同じ形にした。載せる形だと調整ねじが胴の脇に
立つので、六角レンチが胴をかすめる。吊れば本体は板の下なので、**板の上は
完全に開いた面**になり、ねじの頭が全部いちばん上に来る。
副産物として**下段の立板が要らなくなった**（固定板を横材の上面へ直に
載せて溝ナットで留める）。部品が 2 枚減り、外形も内側へ寄る。

⚠ **走査面の高さは横材の上面（Z=135）から下向きに決まる。** 固定板 t6 →
すきま 12 → 可動板 t6 → 検出面まで 47.4 を引いて **69.6**。
上へは動かせない — 椅子の座板（Z 150..162 / X 130..460）が前の LiDAR の
真上にあり、調整ねじの頭（上端 145）はその下に収まっていなければならない。
下へも動かせない — 横材の上面より下へ座を下ろすと、固定板が横材の側面と
しか当たらず溝ナットで留まらない。

⚠ **前の LiDAR の水平出しは、椅子を載せる前にやること。** ねじ 4 本のうち
-X 側の 2 本（X=425）と、固定板を横材へ留める 2-M5 は、座板（X≤460）の
真下に来る。椅子は 4-M6 で外せるので、順序を守れば工具は入る
（`screw_place` が「頭の外が chair_5go に塞がれて工具が入らない」と出すのは
このため。椅子マウント自身の 8 本も同じ理由で同じ指摘が出ている）。

末尾の ⚠ ブロックに残してある。

**表示器の留め方（2026-08-07 に作り直した）。** 横材 `disp_beam` は後柱の -X 面に
**重ねて**置いてあり、`BRACKET` と宣言しながら金具もねじも 1 つも無かった。
描き忘れではなく**描けなかった**: 重ね継手には標準の L 金具が入らない。金具は腕を
それぞれの材の**軸方向**へ伸ばして初めて穴が溝の芯に乗る（`L.bracket()` の穴は内隅から
11mm、溝の芯は材の縁から 10mm。腕を軸と直角に伸ばすと必ず 1mm ずれる）。幅 20 の金具では
横材の溝（X -295.4）と柱の溝（X -275.4）が 20mm 離れていて、両方に届く向きが存在しない。
→ **柱の内側に渡す T 継手**（`mast_cross` と同じ形）にして、横材の上下の入隅に
`L.bracket()` を各端 2 個・計 4 個入れた（M5 溝ナット 8 本）。
取付枠は**横材をくわえるコの字**にした。横材の -X 面の溝は画面（|Y|≦97.5）の真裏に
あるので、そこへ M5 を打つと頭が画面の中に入る。爪を上下へ回せばねじは**上下の溝**に
入り、画面と重ならないうえ上下 2 点でつかむので倒れも止まる。

**表示器は「筐体」と「画が出る面」を分けて描く。** 195×122×14 の箱ひとつだと材質が
1 つしか付かず、ビューアでもプロモでも白い板が 1 枚立っているだけになる（実際そうなって
いた）。実品は 8 型 16:10 なので画は対角 203.2mm から **172.3×107.7**（`DISP_SCR_W/H`）、
まわりに左右 11.4 / 上下 7.2 のベゼルが残る。`disp_panel` にその座を彫り、材質 `SCREEN` の
`disp_screen` を `PRESS`（インロー）で落としてある。⚠ **映っている内容は形として持たない**
（画素であって部品ではない）。プロモは `promo/tex/screen.png` を Emission で貼り、ビューアは
自発光にして点いていることだけ出す。詳細は `cad/promo/README.md`。

### シミュレーションが見つけた設計不具合（すべて修正済み）

物理で動かして初めて出た問題。**どれも図面だけ見ていたら見落とす類**である。

### 剛体シムの限界（結果を読むときの注意）

* 雑巾は 200×300×3mm の剛体プレート。布のたわみ・空力・はためきは扱えない。
  → 弾道と布姿勢は `gpusim/` の専用シムが担当し、こちらは機構の成立性のみを見る。
* 「くさびが布端を持ち上げて山の下に滑り込む」挙動は剛体では表現できないため、
  挿入中だけ山の自重を打ち消し、上押さえが降りた時点で櫛歯へ固定拘束する形で代用した。
  **したがって「回収 10/10 枚」は“機構配置が正しい”ことの確認であり、実機の回収成功率の予測ではない。**
  成功率は 8/29 の Go/No-Go 実験（戦略書 §5）で実測すること。
* 走行はメカナムの摩擦モデルではなく速度指令ドライブ。車体反力は装填系にのみ効く。

## 12. 静解析（3D 梁要素 FEM）

`cad/scripts/fea_frame.py`。骨格（HFS5-2020）を 3次元 Euler-Bernoulli 梁要素で解く。
部材交差点に自動で節点を立て、4輪接地点をピン支持とする。

| 荷重ケース | 砲塔取付面の変位 [mm] | バケツ位置の変位 [mm] | 最大曲げ応力 [MPa] | 支配部材 | 判定 |
|---|---|---|---|---|---|
| LC1 自重のみ（静止） | 1.25 | 1.67 | 15.7 | 砲塔台座横梁 | OK |
| LC2 前後加速 1.5m/s² | 1.08 | 1.31 | 16.5 | 砲塔台座横梁 | OK |
| LC3 横加速 1.5m/s²（旋回・被弾回避） | 1.72 | 2.22 | 16.0 | 砲塔台座横梁 | OK |
| LC4 グラバー全開（片持ち最大） | 0.99 | 1.40 | 12.5 | 砲塔台座横梁 | OK |
| LC5 射出反力（雑巾48g×9m/s を20msで） | 1.36 | 1.60 | 19.9 | 砲塔台座横梁 | OK |
| LC6 教壇へ接触停止（0.8m/s→0 を0.15s） | 1.25 | 1.67 | 15.7 | 砲塔台座横梁 | OK |

許容応力 90 MPa（A6005C-T5 耐力200MPa / 安全率2.2）、節点数 54、部材数 70、総押出長 16.8 m

### 読み取り

* **応力は全ケースで許容の 1/4 以下**（最大 19.9 MPa / 許容 90 MPa、安全率 4.5）。
  骨格は強度ではなく **剛性（たわみ）で決まっている**。
  → 断面を細くする軽量化より、トラス配置を見直す方が効く。
* 砲塔取付面の変位はケース間で **0.99〜1.72mm（差 0.73mm）**。
  静的なたわみは弾道テーブルの較正で吸収でき、**効くのは差のほう**。
  0.73mm は射出点 3m 先で約 0.7mm 相当 → 命中率への寄与は無視できる。
* 支配部材は **砲塔台座横梁**。ここを 2020→2040 に上げると砲塔面の変位は約 1/3 になる（+0.34kg）。
  質量マージンが確保できたら最初に投資すべき箇所。
* 最も応力が高い荷重ケースは **LC5 射出反力**。雑巾48g×9m/s を 20ms で与えた反力（21.6N）でも 19.9MPa。

### モデル化の前提（結果の読み方）

* 節点は剛結。実機のアルミフレーム用ブラケットは完全剛ではないので、**実際のたわみは
  この値より大きい**。結合部の回転剛性が支配的になり得るため、ボルトの締結トルク管理と
  ブラケットの二重使用（角部）を前提とする。
* バケツ受け板・旋回リング板は面内剛性を等価梁に置き換えている。
* ねじり定数 J は溝付き中空断面のため 1.2×10⁴ mm⁴ と仮定（保守側）。

## 14. スーパー雑巾（400×600・140g・1枚200点）のハンドリング

| 引きずり摩擦 | 0.2 × 0.14kg × 9.81 = **0.27 N** | 机が動く力 39N の 0.7% → 反則リスクなし |
| 上押さえ 220×400 | 中央をクランプ | OK |
| ニップ有効幅 570 vs 布幅 600 | 中央570を把持、両端15mmずつフリー | OK |

**140mm のはみ出しは許容する**。布は柔らかいので櫛歯先端で折れて垂れ、引き込みとともに
机の縁から落ちて櫛歯の上に乗る。引きずり摩擦 0.27N は机を動かす力（39N）の 0.7% しかないので
4.1.4a の反則にはならない。剛体シムではこの「垂れ」を表現できないため、
**8月の実機実験で必ず確認する項目**として §8 に追加する。

なお FAQ 4.1 Q2 で「装填しやすいように折る・畳む」ことは合法なので、
実験でうまくいかない場合は **場外で 200×600 に一度折ってもらう** 運用に切り替えられる
（この場合ニップギャップを 1.5→3.0mm に偏心カムで開く）。

### 見つかったこと（運用シーケンスを変更した）

射出ローラーのスピンアップは**素モーター 1軸 20A**で回すと 0.44 秒だが、2軸で 40A になり
それだけで規定違反になる。1軸 10A に制限すると 0.88 秒。

問題は**いつスピンアップするか**だった。当初のシーケンスは「射撃位置へ前進しながら」で、
このとき駆動 10.5A と競合して合計 36A → 配分器が駆動を 6.5A に絞り、加速が 1.5→0.82 m/s² に落ちる。

→ **引込み中（機体が停止している 4.1 秒間）にスピンアップする**ようシーケンスを変更した。
この局面は装填系 5A しか使っていないので合計 27A で収まり、クランプが一切要らない。
`sim/tr_sim.py` のミッションにも反映済み。

## 16b. 板の余肉と継手の受け方（`plate_audit.py` / `joint_load.py`）

締結の**強度**（16 章）が足りていても、機体は「板が大きすぎる」「受け方が悪い」で
重くなるし壊れる。この 2 つは強度計算には出てこないので、別の検査で見る。

### 板材の余肉 — `scripts/plate_audit.py`

板 1 枚ごとに、**固定宣言（`tr_fix.FIXINGS`）で荷重が通る領域**と板の実肉を
突き合わせる。出すのは 4 種類:

| 種類 | 判定 | 直し方 |
|---|---|---|
| 使用率が低い | 締結・接触が届く面積 ÷ 実肉 < 60% | 荷重経路で抜く（下記）／外形を切る |
| 縁の余り | 一番外の接触から板端まで > 縁代 12mm | その辺を切り落とす |
| 肉抜き無し | 肉抜きを通していない実肉 25,000mm² 超 | 肉抜きを入れる |
| 板厚過大 | 支点間を渡る帯として安全率 > 4 | 1 段薄い板へ |
| 台帳の食い違い | 手書きの質量と体積×密度が 30% 以上ずれ | 台帳か形のどちらかを直す |

**板厚は曲げ応力だけでは決まらない。** ボルト穴の支圧（t ≥ 0.5d）・取り回し
（t ≥ 支点間/200）・切削の実用下限（t ≥ 2.0）を下限として持たせている。
これを入れないと、検査はガセットにまで「t0.8 で足りる」と言ってくる。

### トラス肉抜き（`L.plate_iso` / `L.plate_slots`、生成器は `src/lattice.py`）

板を抜く手は 3 つだけにしてある。

| 手 | 使いどころ | 出てくる形 |
|---|---|---|
| `topo_plate` | 構造板（`scripts/topo_opt.py` が解いた輪郭を読む） | 外形そのものが荷重の形 |
| `plate_iso` | 幅のある板 | 正三角形の格子（アイソグリッド） |
| `plate_slots` | 帯のように細長い板 | 長手に並べた長穴（スタジアム形） |

**2026-08-07 に丸穴（旧 `L.lighten` / `L.lighten_path`）は捨てた。** 丸は
「穴どうしを rib 以上離せば残る材料は必ず一続きになる」ことが自明で実装が
楽だったが、**分断しないことを穴の側で保証していた**ので、残る材料の幅が
径とピッチの引き算の余りになる。いちばん細いところで強度が決まるのに、
そこが設計値ではない。

トラス肉抜きは逆で、**先にリブの網（三角格子 / 梯子）を決めて隙間を抜く**。
網は定義から連結なので分断は構成で保証され、リブ幅は板のどこでも設計値
ちょうど（7〜12mm）になる。三角形は面内で筋交いが入った状態なので、
同じ質量ならせん断に強い。置き換えた 6 種 11 枚で **−227g**。

割り付けの決まり:

* 縁の残肉 `edge` は既定 `max(rib, 2×板厚)`
* 座面・軸穴・ボルトの座は `guards`（円）として、半径 + rib だけ膨らませて外す
* 締結から荷重点へ力が流れる帯は `bands`（線分 + 半幅）として外す。
  半幅は せん断 F/(2tτ) と リブ下限 `BAND_MIN` = 6mm の大きい方。
  ⚠ **帯は膨らませない**（帯そのものが残したい材料。膨らませると板が抜けない）
* 範囲からはみ出す穴は捨てずに切り詰め、切り口は丸め直す。
  元の半分未満に痩せた穴は開けない（縁にかけらが並ぶのを止める）
* 抜いたあと材料が一続きでなければ例外にする

限界: 面内の荷重伝達だけの近似で、面外曲げは見ていない。旋回アームのような
**曲げで持つ板には使わない**（穴が断面係数をそのまま削る）。適用したのは
上押さえプレート・棚板・キャリッジ横梁/側金具・レール取付プレート・
モーターマウント（どれも面内で持つ板）。

⚠ **板の輪郭を変えたら `scripts/screw_place.py` を回し直す。** ねじの位置は
凍結生成物で、輪郭が変わると座面が穴に落ちる。順序は
`screw_place → topo_cache → topo_opt → export_meshes → tr_urdf → export_fab → check_all`。

### 継手の受け方 — `scripts/joint_load.py`

宣言されている全締結を幾何から見て、次の 5 つを出す。

| 種類 | 症状 | なぜ悪いか |
|---|---|---|
| 切り口受け | 板の端面（板厚 × 幅）で受けている | 座面が数百 mm² しか無く、曲げで穴が伸びる |
| てこ | 荷重の重心が座面の外 | ねじが引張＋てこで効く（せん断で受けるべき） |
| 溝ナット引き抜き | T ナットが抜ける向きに荷重 | 溝の肩が変形する。1 個 500N 目安 |
| 長い片持ち | 腕 ÷ 受け幅 > 4 | 受けを 2 点に離すか斜材が要る |
| ガセット無し | 押出材の直角結合に補強が無い | 回転剛性がボルトの摩擦だけになる |

**受けは「自分にぶら下がっていない相手」**として数える。接触を全部まとめて
座面にすると、上に載る部品まで受けに数えて、どの部材も「全長で受けている」
ことになる（片持ちのマスト腕がそれで検出できなくなった）。

## 18. 締結の実体化と、干渉チェックの拡張で見つかった不具合

### ボルトを CAD に実体として入れた

`scripts/fasteners.py` の J1〜J10 に対応するボルトを STEP に実体で置いた
（穴だけでなく頭部と軸を持つ）。座面の位置と本数が図面から読めるので、
組立時に「どこを何本で締めるか」を CAD だけで確認できる。ねじ山は描いていない
（STEP が重くなるだけで設計判断に効かないため）。

その後、**骨格の締結を実体化**して 56 → **148 本**にした（→ 次節）。

### ⚠ 締結具の員数を数えたら、概算 0.70kg が実は 3.05kg だった

`scripts/fastener_bom.py`（`out/fasteners_bom.md`）で、固定宣言の `note`
（"4-M4 PCD35" など）と**実体のねじ**を突き合わせて員数を出せるようにした。

分かったこと:

* 締結具は全部で **1,544 個・3,051g**。質量台帳の概算「ボルト・ナット・
  スペーサ類 **700g**」の **4.4 倍**だった。
* 内訳の最大は**後入れナット（溝ナット）M5 が 224 個・455g**。アルミフレームの
  機体では、ナットがボルトと同じだけ質量を持つ。
* これで総質量は **34.84 → 37.19kg**。規定 35.0kg を **2.19kg 超過**する。
  §7 の削減レバー（合計 −2.6kg 見込み）を**実施しないと成立しない**。
  概算の中に隠れているあいだは「余裕 160g」に見えていた。

数え方は `tr_lib.fastener_joints()` / `fastener_tally()` の 1 か所にだけ置き、
質量台帳（`LEDGER`）と員数表の両方がそれを呼ぶ。ずれたら
`scripts/fastener_bom.py` が NG を出す。

### 骨格の L 金具 46 個にねじを実体で入れた

「BRACKET と宣言してあるのに、金具を留めるねじが 1 本も描かれていない」
状態だった。ここは上部質量の転倒モーメントが全部通る主経路なので、
92 本（金具 1 個につき腕 1 枚に 1 本）を実体で置いた。

そのとき出た幾何の問題と対策:

| 症状 | 原因 | 対策 |
|---|---|---|
| 頭どうしが 102mm³ 重なる（46 個すべて） | 2 本の軸線が内隅の上で**交差**し、頭がその交点へ向かって伸びる。腕 17mm では離せない | 腕 a を**皿ねじ**にして頭を材の中へ沈めた |
| 幅方向へ 5mm ずらしたら 24,084mm³ 削った | **幅方向は溝と直角**。5mm ずらすとねじ φ5 が溝口 6mm から外れて材を噛む | 幅方向へは振らない（皿ねじで解決） |
| 柱脚の直付けねじが溝ナットに 0.5mm まで接近 | 金具でも柱でも同じ継手を留めていた（二重）。しかも頭が**中空の柱の中**で工具が入らない | 直付け 8 本を削除。金具 2 個 × 各 2 本で受ける |
| X=+210 の金具で六角レンチが入らない | 前輪モーターマウント（X 235..365）が工具空間 45mm を塞ぐ | その station だけ金具を -X 面へ回した |

### 干渉チェックのペアを 9 → 13 に拡張して 4 件を検出・修正

スライドレール群とマストを検査対象に入れていなかったため、以下が見逃されていた。
**可動部が絡む干渉は、検査ペアの穴がそのまま設計の穴になる**という教訓。

## 21. 装填の頑健性（モンテカルロ）— 8/29 Go/No-Go の事前評価

`cad/sim/tr_montecarlo.py`。実戦で必ず出るばらつきを入力して、山の一括回収が
成立する割合を出す。**成功の判定を「押さずに山の下へ入ったか」まで厳格化**した点が要。

### 成功条件

1. 10枚すべてが櫛歯の矩形（260 × 465）の上にある
2. **挿入で山を 10mm 以上押していない**（押したなら「下に入れた」ではない）
3. 机の移動が 2mm 未満（4.1.4a）

### 頑健性の限界

| ばらつき | 成功率 | 山の最大押し出し | 失敗モード |
|---|---|---|---|
| ×1: 山±20mm/±5°・停止±10mm | **100%** (8/8) | 0 mm | — |
| ×2: 山±40mm/±10°・停止±20mm | **100%** (8/8) | 1 mm | — |
| ×3: 山±60mm/±15°・停止±30mm | 75% (6/8) | 114 mm | 櫛歯が山の前面を押した ×2 |
| ×4: 山±80mm/±20°・停止±40mm | 50% (4/8) | 138 mm | 押し出し ×2、部分把持 ×2 |

**破綻点は ×2 と ×3 の間**。つまり運用要件は:

* **山の置き位置精度 ±40mm・±10°以内**（スポッターが場外から整える。FAQ 4.1 Q2 で合法）
* **車体の停止精度 ±20mm 以内**（LiDAR自己位置 + 前面ToF×2 で達成する目標値）

この2つを満たす限り 100%。超えると「櫛歯が山の下に入らず前面を押す」失敗が出る。
→ **ToF による机エッジの最終合わせは必須**（LiDAR単独の ±30mm では ×3 相当になり 75% まで落ちる）。

### この解析で見つかった設計不具合

| # | 症状 | 原因 | 対策 |
|---|---|---|---|
| S19 | 櫛歯が山を **235mm 押していた**（緩い判定では見えていなかった） | キャリッジ後端横梁がヒンジより**前**にあり、櫛歯の上に90mm張り出していた。山の下に入る前に前面を押す | 横梁をヒンジより後ろ（+X側）へ移動。上押さえのガイド軸も z=818〜968 へ上げて山の上端(795)を越えさせた |
| S21 | 上押さえが山を 9mm 潰し、押付力が 50N（設計は25N）に張り付いていた | ストロークが 80mm と 10mm 長すぎた。S19 修正前は山が押し出されていて押さえの下に無く、この問題が隠れていた | ストロークを **70mm** に短縮（下限でパッド下面 796 ＝ 山の上端にちょうど接する）。実測押付力 13.6N / 上限25N |
| S20 | 机が触れていないのに 5mm 動く | 机を「天板＋脚を拘束でつないだ多体」で作っており、ソルバーの残差で毎回ドリフトしていた | 机を**単一剛体**（複合形状）に変更。基準走行での移動量が **0.0mm** になり、反則判定が意味を持つようになった |

S19 は「10/10 回収」という良い数字の裏で起きていた。**判定を厳しくしなければ最後まで見つからなかった**。

## 22. 挿入中止（リミットSW）の有効性 — 「机を押す事故」の定量的な保証

戦略書 §4.3.2 は「挿入時にフォーク根元のリミットSWが抵抗を検知したら即後退。
**机を押す事故の防止を最優先**」としている。これをシミュレーションで実装・検証した。

実装（`sim/tr_sim.py`）: 挿入中に山が **5mm** 以上動いたら中止し、
フォークを引き戻して上押さえは降ろさない（押さえを降ろすと山を挟んだまま机を引きずる）。

### 結果

| ばらつき | 成功率 | 中止件数 | 中止の検知量 | **机の移動（最大）** |
|---|---|---|---|---|
| ×1: 山±20mm/±5°・停止±10mm | 100% | 0 | — | **0.0 mm** |
| ×2: 山±40mm/±10°・停止±20mm | 100% | 0 | — | **0.0 mm** |
| ×3: 山±60mm/±15°・停止±30mm | 75% | 2 | 5mm で検知 | **0.0 mm** |
| ×4: 山±80mm/±20°・停止±40mm | 50% | 4 | 5mm で検知 | **0.0 mm** |

**どのばらつきでも机は 1mm も動かない。** 失敗は「回収できなかった（＋6秒のロス）」に留まり、
**反則（4.1.4a）には至らない**。これが本設計の安全側の作り込みの核心である。

中止後に山が最大 138mm ずれるのは、引き戻し時に山が櫛歯に引っかかって連れられるため。
机には影響しないが、**やり直し前にスポッターが山を整え直す必要がある**
（FAQ 4.1 Q3 でフィールド外からの整えは合法）。自動リトライだけでは復帰できない
（山が奥へずれるとフォークのストローク 424.6mm では届かなくなる）ので、
**リトライは「人が整える → 再接近」の運用とセット**にすること。

### 旋回体ケーブルのねじれ余長

砲塔ハーネスはヨー軸の中心から入れるので曲げは生じないが、**ねじれ**は残る。
束径 φ12 のケーブルで ±30° を許容するには、経験則で **自由長 ≥ 10×束径 = 120mm** が要る。
→ 車体側の最終クランプを **z=750**、旋回体側の最初のクランプを **z=870** に置いて
自由長 120mm を確保した（CAD の経路もこの位置に修正済み）。

## 24. 命中率の誤差バジェット — 「どの誤差が命中率を決めているか」

`cad/scripts/accuracy_budget.py`。gpusim 較正つきの ShotSolver で狙いを出し、
機構・制御・センサーの誤差を注入して「横棒に上から被せる」判定をモンテカルロする
（20,000試行）。命中の定義は gpusim の下降当て戦略に合わせ、
**横棒の 0〜25cm 上を降下中に通過し、横ずれ ±0.30m 以内**とした。

狙い: 初速 **8.37 m/s** / 仰角 **67°**（横棒の 12cm 上を降下中に通す）

| 誤差源 | 1σ | 単独での命中率 | 備考 |
|---|---|---|---|
| 初速（ニップ隙間・スリップ） | 2.0% | 35% | 隙間1.5±0.2mm の圧縮率差。実測で詰める |
| 雑巾の個体差（質量・毛羽） | 1.5% | 44% | 48g±3g。競技委員会支給で選別不可 |
| 布のニップ投入姿勢 | 0.6° | 85% | gpusim の meanMiss 0.044m 相当。**支配的** |
| 初速（ローラー回転数制御） | 0.5% | 89% | C620 の閉ループ。エンコーダ分解能は十分 |
| 仰角（ウォーム40:1 バックラッシュ） | 0.15° | 100% | 図の片フランクすきま 0.12mm → 全遊び 0.24mm/基準円半径 30mm = 0.458°、一様分布とみて 1σ=0.13°。逆駆動なし |
| ヨー（ベルト3:1 バックラッシュ） | 0.2° | 100% | — |
| 射出点の変位（骨格のたわみ） | 0.0003m | 100% | 静解析の荷重ケース間差 0.73mm の 1σ 相当 |
| 自己位置推定（LiDAR + ICP） | 0.01m | 100% | 目標 ±30mm の 1σ |
| **全誤差を同時に入れた命中率** | | **26%** | |

### 初速の再現性を詰めるとどうなるか

| 初速の 1σ | 命中率 |
|---|---|
| 隙間2.0% + 個体差1.50% | 26% |
| 隙間1.0% + 個体差0.75% | 45% |
| 隙間0.5% + 個体差0.38% | 62% |

### 厚み計測フィードフォワードで、どこまで詰められるか

シンギュレータのピックローラー変位（重送検知用のホールセンサー）で1枚ごとの厚みを測り、圧縮率→スリップ率→初速のずれを予測して、ニップ到達までの 0.33 秒でローラー回転数を補正する。

| 厚みセンサーの分解能 | 補正後に残る初速 1σ | 命中率 |
|---|---|---|
| 1.00 mm | 2.17% | 28% |
| 0.20 mm | 0.43% | 49% |
| 0.05 mm | 0.11% | 52% |
| 0.02 mm | 0.04% | 52% |

> 厚みの個体差そのものは 1σ=0.2mm。分解能 0.05mm のセンサーなら残差 0.11% まで落ちる。

### 対策を積み上げたときの到達点

| 段階 | ニップ隙間 1σ | 個体差 1σ | 命中率 |
|---|---|---|---|
| 対策なし（偏心カム・FFなし） | 2.0% | 1.50% | **26%** |
| + 厚みFF（分解能0.2mm） | 2.0% | 0.43% | **32%** |
| + テーパくさび1:20（分解能3.5µm） | 1.0% | 0.43% | **49%** |
| + 回転数降下から初速を実測して補正 | 0.3% | 0.43% | **65%** |

### 結論 — 精度投資はニップに集中させる

* **命中率は初速の再現性でほぼ決まる。** ニップ隙間 2% のばらつきだけで単独 34%、
  雑巾の個体差 1.5% だけで 44% まで落ちる。
* **機構の精度（仰角・ヨーのバックラッシュ）と自己位置推定は、単独では命中率を 1% も落とさない。**
  骨格のたわみ（静解析で 0.73mm）も同様に無視できる。
  → **砲塔の高精度化に投資しても命中率は上がらない。**
* 初速の 1σ を半分（隙間1.0% + 個体差0.75%）に詰めれば **27% → 45%**、
  1/4（0.5% + 0.38%）まで詰めれば **62%**。

これは戦略書 §2.1 が置いていた「旗 70〜85%」という前提に対して厳しい数字である。
70% に到達するには初速の 1σ を **0.4% 級**まで詰める必要がある。具体的には:

1. **ニップ隙間の全数管理** — 5点の隙間差 0.2mm 以内（`ASSEMBLY.md` 工程5に反映済み）
2. **射出ごとの実回転数ログと補正** — 1発ごとに周速を測り、次弾の指令に反映（戦略書 §4.1 と同じ）
3. **雑巾の個体差の吸収** — 質量は選別できないので、**ニップ通過時間から実効初速を推定**して
   その場で仰角を微修正するフィードフォワードを検討する
4. それでも届かない場合は、**命中判定の窓が広い目標（机①②・固定バケツ）の比率を上げる**
   ——期待値の再計算が必要（戦略書 §2.1 の見直し）

## 25. 厚み計測フィードフォワード — 雑巾の個体差を機械で吸収する

雑巾の質量・毛羽の個体差（初速 1σ 1.5%）は競技委員会支給品なので選別できない。
しかし **1枚ごとの厚みを測れば、その個体差は予測できる**。

原理: ニップ圧縮率 c = (t − gap)/t、初速のずれ dv/v = k·dc。
厚み t を測れば c が決まり、必要な回転数の補正量が出る。
**シンギュレータからニップまで 0.33 秒**あり、ローラーは 10A で 226 rad/s² の角加速度を
持つので、その間に ±3.4 m/s の速度変更ができる。±2%（0.17 m/s）の補正は余裕で入る。

センサーは **すでに設計にある重送検知用のホールセンサー**（ピックローラー揺動アームの
変位を読む）をそのまま使う。追加コストはゼロ。

| 厚みセンサーの分解能 | 補正後に残る初速 1σ | 命中率 |
|---|---|---|
| 1.00 mm（分解能不足） | 2.17% | 28% |
| **0.20 mm** | 0.43% | **49%** |
| 0.05 mm | 0.11% | 52% |
| 0.02 mm | 0.04% | 52% |

**分解能 0.2mm で十分**（0.05mm まで上げても +3% しか改善しない）。
安価なリニアホールIC（SS495A 級）で到達できる領域である。
0.2mm より先は **ニップ隙間の管理精度（1%）が支配的**になるので、
そこから先は「隙間の全数管理」に投資する。

* 命中率 **27%（対策なし）→ 49%（厚みFF + 隙間1%管理）→ 63%（隙間0.5%まで詰める）**
* CAD にホールセンサー ×2 と揺動アームを追加済み（ホッパー前壁上、\|Y\|=210）

> 係数 `SLIP_COEF = 0.45`（圧縮率→初速の比）と厚みの個体差 1σ=0.2mm は仮定値。
> **7月中の試射で必ず実測すること**。この2つが本設計で最も不確かなパラメータであり、
> 命中率の予測精度を直接支配する。

## 26. ニップ隙間の管理 — 偏心カムでは 14 倍足りなかった

厚みフィードフォワードを入れると、次に支配的になるのは **ニップ隙間の管理精度**。
命中率の目標から逆算すると、隙間 1.5mm を **±15µm（1%）** で管理する必要がある。

## 3. 射出ごとの初速の実測（既存エンコーダだけで可能か）

射出でローラーの運動エネルギーが雑巾へ移る。その回転数降下を測れば初速が逆算できる。

| 項目 | 値 |
|---|---|
| 定常角速度 | 186 rad/s（1776 rpm） |
| 雑巾へ渡るエネルギー | 1.68 J |
| 1射あたりの角速度降下 | **6.6 rad/s（3.5%）** |
| C620 の回転数分解能 | 1 rpm = 0.105 rad/s |
| 降下量の相対分解能 | 1.6% |
| **初速の測定精度（E∝v² なので 1/2）** | **0.8%** |

### 設計変更: 偏心カム → テーパくさび 1:20

当初案の偏心カム（偏心1mm・30分割）は分解能 **209µm** で、目標 15µm の **14倍粗い**。
手回しで目盛りが読めても、その分解能では隙間を追い込めない。

→ **テーパくさび 1:20（M4×0.7 駆動）に変更**。分解能 **3.5µm**（目標の 1/4）で、
CNC で作れて自己保持する。CAD にも上ローラー軸受を押すくさびとして追加した。

### 射出ごとの初速の実測 — 追加センサーなしで 0.8%

射出でローラーの運動エネルギーが雑巾へ移る。**その回転数降下（3.5%）を C620 の
エンコーダで読めば、初速を 0.8% 精度で実測できる**。これを移動平均すれば、
摩耗・発熱による隙間ドリフト（RSS 0.025mm = 初速 0.75%）をそのまま追従補正できる。
`control/tr_control.py` の `MuzzleFeedForward.measure_from_rpm_drop()` に実装済み。

### 命中率の改善ロードマップ（積み上げ）

| 段階 | ニップ隙間 1σ | 個体差 1σ | 命中率 |
|---|---|---|---|
| 対策なし（偏心カム・FFなし） | 2.0% | 1.50% | **26%** |
| + 厚みFF（分解能0.2mm・追加コスト0） | 2.0% | 0.43% | **32%** |
| + テーパくさび1:20（分解能3.5µm） | 1.0% | 0.43% | **49%** |
| + 回転数降下から初速を実測して補正 | 0.3% | 0.43% | **65%** |

**26% → 65%**。戦略書 §2.1 が置く「旗 70〜85%」にはまだ届かないが、
**追加のセンサーもアクチュエータも要らずにここまで来る**。
残りは実測でパラメータ（SLIP_COEF・厚み個体差・捕捉窓）を詰めてからの判断になる。

## 27. 試合中の自動較正 — 32射で間に合うか、そして戦略書の 70% に届くか

射出ごとに回転数降下から実効初速を測り（0.8% 精度）、EWMA で系統誤差を推定して
次弾の回転数に反映する。**1試合で撃てるのは32枚しかない**ので、較正が間に合うかが問題。

1試合 32 射 × 400 試合。試合中に系統ドリフト **+1.2%**（ニップの発熱・摩耗）が線形に入る想定。

| 較正方式 | 命中率 | 初速の平均残差 | 残差 1σ |
|---|---|---|---|
| 較正なし（開ループ） | **67%** | 0.71% | 0.87% |
| EWMA α=0.10（推奨） | **73%** | 0.50% | 0.62% |
| EWMA α=0.25 | **70%** | 0.51% | 0.64% |
| EWMA α=0.50（速い） | **65%** | 0.59% | 0.75% |
| EWMA α=0.10 + 試合前6射で較正 | **73%** | 0.51% | 0.63% |

- 較正なしだと命中率 67%、最良の EWMA α=0.10（推奨） で 73%。
- **α=0.10 の時定数は約10射**。試合中のゆっくりしたドリフトには十分間に合う。
  一方 α を大きくすると測定ノイズ 0.8% をそのまま指令に流し込むので逆効果になる。
- ただし **試合前に 6 射だけ較正しておく**と、序盤の外しが消えてさらに良くなる。練習で必ずやること。
- α を大きくしすぎる（0.50）と測定ノイズ 0.8% を拾って逆効果。

### 結論 — 旗 70% の見通しが立った

* **較正なし 67% → EWMA α=0.10 で 73%。** 戦略書 §2.1 が置く「旗 70〜85%」の
  下限に到達する見通しが立った（ただし後述の仮定つき）。
* **α を上げすぎると較正なしより悪くなる**（α=0.50 で 65%）。
  測定ノイズ 0.8% をそのまま指令に流し込むため。**α=0.10 を実装値とした**
  （`control/tr_control.py` の `MuzzleFeedForward.CAL_ALPHA`）。
* ドリフトは試合中ゆっくり進むので、速い追従は要らない。**遅い追従＋低ノイズ**が正解。

### ここまでの積み上げ（すべて追加部品ゼロ）

| 段階 | 命中率 |
|---|---|
| 素の設計（偏心カム・補正なし） | 26% |
| + 厚みフィードフォワード（既存ホールセンサー流用） | 32% |
| + テーパくさび 1:20（分解能 3.5µm） | 49% |
| + 回転数降下からの初速実測（隙間ドリフト吸収） | 65% |
| + EWMA 自動較正 α=0.10（系統誤差の追従） | **73%** |

> **この 73% は、以下の仮定の上に立っている。実測で崩れる可能性がある。**
> * `SLIP_COEF = 0.45`（圧縮率→初速）… 7月の試射で実測
> * 雑巾の厚み個体差 1σ = 0.2mm … 支給品を実測
> * 捕捉窓「横棒の 0〜25cm 上を降下中」… gpusim の 37% と整合するよう置いた値
> * 布のニップ投入姿勢 1σ = 0.6° … gpusim の meanMiss から逆算
>
> 特に捕捉窓は命中率に直結する。**8月の弾道テーブル本計測（1,000射）で
> 実際の捕捉率を測り、この表全体を較正し直すこと。**

### 見つかった穴: 射出速度 7m/s では固定バケツが全て射程外

## 29. gpusim との座標系の食い違いを解消 — 射出速度域が半分になった

前節で「gpusim の最適解（8.25m/s・67°）が真空モデルでは横棒に 13cm 届かない」という
食い違いが残っていた。gpusim のソースを読んで原因が分かった。

### 原因: gpusim は Y-up・射出点が原点

`gpusim/ragsim/targets.py` の `FlagTarget` は

```
bar_y: float   # 3.0   ← 横棒の「高さ」
bar_z: float   # 標的距離 D
```

つまり **Y が上・Z が前方**で、しかも射出点は原点（高さ 0）。
必要な上昇量は **3.0m**（こちらが 2.1m と読み違えていた）。この 0.9m の差で
較正が破綻していた。

### 正しい補正係数 — 布は揚力で真空弾道より飛ぶ

| 仰角 | 真空解 | gpusim（布シム） | 補正係数 |
|---|---|---|---|
| 48° | 11.15 m/s | 8.00 m/s | **0.717** |
| 67° | 8.90 m/s | 8.25 m/s | **0.927** |

布は平板なので**揚力が乗り、同じ距離を真空弾道よりずっと低速で飛ぶ**。
低仰角ほど滞空中の水平速度が高く揚力が効くので補正が強い。
`ShotSolver._pitch_calib()` に実装（2点の線形内挿。**近距離 <2.5m には掛けない**
——滞空が短く揚力が乗らないため。近距離は7月に別途実測する）。

### 結果: 必要な射出速度域は 7〜15 m/s ではなく **2.7〜6.5 m/s**

戦略書 §4.1 の「射出速度 7〜15m/s」は真空弾道で見積もった値だった。
布の揚力を入れると、同じ目標を**ほぼ半分の速度**で狙える。

| 影響 | 内容 |
|---|---|
| ローラー回転数 | 3183 rpm → **1380 rpm**。スピンアップは 0.88s → **0.64s** |
| ローラーの蓄積エネルギー | 38 J → **14 J**。射出時の電流スパイクが小さくなる |
| 電流バジェット | スピンアップの負担が減り、30A 制約がさらに楽になる |
| ローラーの慣性設計 | 現状のままで十分。むしろ余裕がある |

**射出速度域そのものは 2.5〜15 m/s のまま**にしておく（機構の可変範囲は広い方が良い。
実測で必要域がずれても対応できる）。ただし**常用域は 2.7〜6.5 m/s** であることを
制御側の既定値とし、弾道テーブルもその範囲を重点的に埋める。

> この補正係数はまだ **2点**しかない。8月の弾道テーブル本計測（1,000射）では
> **仰角 20〜70° を 5° 刻み × 距離 1.2〜4.5m** を測って、この曲線を実測で置き換えること。

## 30. ローラーは軽量化してはいけない — 慣性が命中率を守っている

必要初速が 9 → 6.5 m/s に下がったので「慣性に余裕ができた。ローラーを軽くして
質量マージンを稼げるのでは」と考えたが、**逆だった**。

常用初速 6.5 m/s、雑巾 48g、スピンアップ電流 10A/軸。

| 案 | 外径 | 実効質量(2軸) | 回転数 | **1射の速度降下** | スピンアップ | 初速測定精度 | 質量差 |
|---|---|---|---|---|---|---|---|
| 現行 φ90 / リング 0.68kg | φ90 | 0.68 kg | 144 rad/s | **3.5%** | 0.64 s | 1.03% | +0 g |
| φ90・リング半分に軽量化 | φ90 | 0.34 kg | 144 rad/s | **7.1%** ⚠ | 0.32 s | 0.51% | -340 g |
| φ90・リング 2/3 に軽量化 | φ90 | 0.45 kg | 144 rad/s | **5.3%** ⚠ | 0.42 s | 0.68% | -227 g |
| φ110・リング質量そのまま | φ110 | 0.68 kg | 118 rad/s | **3.5%** | 0.78 s | 1.26% | +0 g |
| φ70・リング質量そのまま | φ70 | 0.68 kg | 186 rad/s | **3.5%** | 0.50 s | 0.80% | +0 g |
| φ70・リング 0.55kg（軽量化 -130g） | φ70 | 0.55 kg | 186 rad/s | **4.4%** ⚠ | 0.40 s | 0.65% | -130 g |

- 許容する 1射の速度降下は **3.5%**。降下は射出の最中に起きるので、雑巾の先端と後端で初速が変わる＝初速ばらつきそのもの。
- **軽量化は命中率を直接落とす。** リングを半分に軽くすると降下が 3.5%→7.1% に倍増し、せっかく 0.62% まで詰めた初速ばらつきが台無しになる。**ローラーは軽量化してはいけない。**
- 径を変えても降下率は変わらない（リング質量だけで決まる）。**径を小さくするとスピンアップだけ速くなる** が、ニップの接触弧が短くなって把持が不安定になるので φ90 を維持する。

### 式から出る性質

射出で雑巾に渡るエネルギーは ½·m·v²。それがローラーの回転から出るので

    Δω/ω = ½ · m_雑巾 · r² / J = ½ · m_雑巾 / m_リング

**降下率を決めるのはリングの実効質量だけで、径には依存しない。**
「径を大きくして軽くする」は成立しない（同じ J でも r を大きくすると降下率は r² で悪化する）。

### なぜ軽量化してはいけないか

回転数の降下は**射出の最中**に起きる。つまり雑巾の**先端と後端で射出速度が変わる**。
リングを半分に軽くすると降下は 3.5% → 7.1% に倍増し、
せっかく厚みFF・くさび・自動較正で 0.62% まで詰めた初速ばらつきが台無しになる。

**→ ローラーの質量 0.68kg（実効）は維持する。ここに軽量化の余地はない。**

### 副産物: この降下がバックスピンを作っている

| 項目 | 値 |
|---|---|
| 1射の速度降下 | 3.5%（0.228 m/s） |
| 雑巾長 200mm での回転 | 1.14 rad/s = **65°/s** |
| 滞空 0.9秒での回転量 | **59°**（バックスピン方向） |

戦略書 §4.1 は「上下ローラーの回転数差でバックスピンを独立制御」としていたが、
**回転数差をゼロにしても、この降下だけで 59° のバックスピンが乗る**。
gpusim の最適解が `spin: 0.0`（回転数差ゼロ）だったのは、これで足りているからだと考えられる。

→ 上下ローラーの回転数差は「バックスピンを足す」ためではなく、
**「降下由来のスピンを打ち消して減らす」方向にも使える**。制御の自由度として持っておく。

## 31. 骨格は「変位」ではなく「傾き」で評価する — そして削れる部材は無かった

`scripts/frame_optimize.py`

静解析（§ 骨格の静解析）で応力の安全率が 4.5 出ていた。骨格は強度ではなく剛性で
決まっているはずなので、**剛性を落とさずに押出材（8.38kg・全体の 24%）を削れないか**を、
部材を1グループずつ抜いて確かめた。

### 最初に踏んだ罠: 「部材を抜いたら変位が減った」

素朴に抜いて解くと、バケツ片持ちビームやマスト主柱を抜いたときに**変位が減った**。
これは嘘で、原因は2つあった。

1. 抜いた部材の**自重も消える**ので、その部材が支えていた荷重が宙に浮く
2. 抜いた結果、集中質量の作用点が支持（4輪）から**部材をたどって到達できなくなる**
   のに、解析は解けてしまう（孤立節点が残るため）

→ 判定を3段にした。**① 荷重経路が繋がっているか → ② 機構化していないか → ③ 剛性**。
①で落ちるものは剛性を見る意味が無い。

### 結果

| 判定 | 部材 |
|---|---|
| **必須**（抜くと荷重経路が切れる） | ベース主桁 / ベース内桁 / ベース横桁 / 側面上桁 / 砲塔台座横梁 / マスト主柱(上) / マスト上部横梁 / バケツ片持ちビーム |
| 必要（抜くと変位 7.6 倍） | 側面前柱 |
| 要検討（+14〜18%） | 側面斜材 0.80kg / 側面後柱(下) 0.70kg |
| 削減候補 | 車軸横桁 0.57kg（+5%） |

車軸横桁は駆動モーターマウントの取付桁を兼ねているので、剛性だけで抜けるものではない。
側面斜材はレール取付面の平行度を出す基準にもなっている。
**→ 押出材から削れる質量は無い。** 質量マージン 0.02kg はローラー（§30）にも骨格にも無い。

### 本当の指標は砲塔取付面の「傾き」

変位 [mm] は照準に直接は効かない。効くのは**砲塔取付面の回転**で、しかも
静的な一定分は較正で消えるから、**荷重ケース間で変わる分（振れ幅）だけ**が誤差になる。

| 指標 | 値 | 命中率解析の予算 | 占有率 |
|---|---|---|---|
| 砲塔取付面のピッチ振れ（自重／横加速1.5／グラバー全開の間） | **0.025°** | ピッチ 1σ = 0.62° | **4%** |
| 同 ヨー振れ | 0.008° | ヨー 1σ = 0.20° | 4% |

骨格の剛性は照準予算に対して 25 倍の余裕がある。
参考までに、側面前柱を抜いて変位が 7.6 倍（13.1mm）になっても傾きの振れは 0.186° で、
まだ予算の 30% に収まる。**この機体では、骨格の剛性は命中率のボトルネックではない。**

では骨格の剛性は何のためにあるのか——次の §32 がその答えになる。

## 32. フォークが机に当たる問題 — 1.0mm の隙間に本当に入るのか

`scripts/fork_clearance.py`

雑巾の山をすくう櫛歯は、**机の天板（760）と雑巾1枚目の間**に差し込む。
歯は t2.0、上面 763 / 下面 761 なので、天板から歯の下面まで **1.0mm しかない**。

そしてグラバーは 424.6mm 伸びる片持ちである。§31 で骨格の傾きは照準には効かないと
分かったが、**ここには効く**。伸ばした先で歯先が何mm下がるかを積み上げた。

| 誤差源 | 下がり [mm] | 出どころ |
|---|---|---|
| ① 骨格のたわみ（レール取付点・全閉→全開の差） | 0.06 | 解析 |
| ② 骨格の傾き × 張り出し 424.6mm | 0.40 | 解析 |
| ③ スライドレールのたわみ＋ガタ | 0.60 | **想定値。実機で要実測** |
| ④ 加工・組立公差（RSS 合成） | 0.29 | 見積 |
| **最悪の重ね合わせ** | **1.36** | → 隙間 1.0mm を **超える** |
| 統計合成（RSS） | 0.78 | → 収まる |

骨格由来（①+②）は 0.47mm しかない。**効いているのはレールのガタと組立精度**で、
この機構の成否は骨格ではなくそこで決まる。

### それでも成立する理由 — 下がりは張り出しの2乗で効く

危ないのは「歯先が机の**縁**に正面から当たる」瞬間だけで、
縁さえ越えれば、あとは平らな天板の上なので、下がって歯が天板に触れても
山の下に入っていることは変わらない。

そして**縁をくぐる瞬間はまだ伸ばしていない**。公称の停止位置なら縁での伸長は
200mm（ストロークの 47%）しかなく、下がりは 0.53mm に収まる。

| 停止位置の誤差 | 縁での伸長量 | 縁での下がり | 判定 |
|---|---|---|---|
| −40 mm | 160 mm | 0.44 mm | ✅ |
| ±0 mm | 200 mm | 0.53 mm | ✅ |
| +40 mm | 240 mm | 0.63 mm | ✅ |
| +60 mm | 260 mm | 0.69 mm | ✅ |

停止位置が ±60mm ずれても縁での下がりは 0.7mm 以下で、隙間 1.0mm に収まる。

### 見つかった実装ミス: すくい斜面が天板より下を向いていた

積み上げを作る過程で、**歯先のすくい斜面が 8°・30mm で付いていて、
先端が 758.9mm ＝ 机の天板より 1.1mm 下**にあることが分かった。
これは机の縁に正面衝突する形で、**確実に机を押す**。

シムがこれを見逃していたのは、URDF の衝突形状が斜面を含まず
「歯 = z −2.0〜0」の直方体だけだったため。**見ていないものは検出できない。**

修正の方針は**フォークリフトのツメと同じ**——テーパは**上面だけ**に付け、下面は水平に保つ。

| 項目 | 修正前 | 修正後 |
|---|---|---|
| テーパの向き | 下面ごと 8° 下げ | **上面のみ 3.4°**（t2.0 → t0.2 に研ぐ） |
| 先端下面の高さ | 758.9（天板より 1.1mm 下） | **761.0**（歯の下面と同一＝天板 +1.0mm） |
| 歯の長さ | 260 + 斜面30 | 260 + 先端30 = **290** |
| URDF 衝突形状 | 歯のみ（先端を見ていない） | **先端も直方体で追加**（安全側に厚く） |

下面を水平に保つと何が起きるか——**「縁は高く越え、奥へ行くほど天板に近づく」が
片持ちのたわみからタダで手に入る**。ばねも余分な部品も要らない。

| 伸長量 | 位置 | 歯先の下面高さ | 状態 |
|---|---|---|---|
| 0 mm | 収納 | 760.71 | 天板 +0.71mm |
| 200 mm | 机の縁 | 760.47 | 天板 +0.47mm ＝ **縁を越える** |
| 325 mm | 山の手前 | 760.08 | 天板 +0.08mm ＝ **1枚目の下に入る** |
| 425 mm | 山の奥（全開） | 759.64 | 天板に着地（押付 9N） |

雑巾1枚は t3mm なので、歯先が天板 +0〜3mm にあれば1枚目の下に入る。
進むほど確実に「下」へ入る側へ寄っていく。

天板に着地したときの押付は 9N（先端剛性 26 N/mm ＝ 骨格 59 と レール 46 の直列）。
摩擦 0.2 で水平力 1.8N、机が滑り出す 21N の **9%** にとどまる。
レールの下がりのうちガタの分は力を出さないので、これでも上限側の見積り。

検査は**パラメータではなく形状**を見る（`scripts/validate.py`）。
`_subtree()` でフォークの Compound を取り出し、`.solids()` の最下点を机の天板と比べる。
パラメータで検査すると、将来テーパを付け直したときに素通りしてしまう。

> `_solids()` は葉をそのまま返すので、**親に付いた Location が乗らない**。
> グループ単位で位置を与えている部分を世界座標で測るときは `_subtree()` を使うこと。

### 回帰テスト: 修正前の形状でシムが検出できるか

「衝突形状を足したから検出できるはず」は確かめないと信用できない。
`FORK_TIP_CLEAR` を −1.1（＝修正前の 758.9mm）に戻してシムを回した。

| 形状 | 机への接触 | 机の移動 |
|---|---|---|
| 修正前（先端 758.9・衝突形状も旧） | **0 回**（見えていない） | 0.0 mm |
| 修正前（先端 758.9・衝突形状は新） | **884 回**（初回 t=5.08s, F=1.9N） | 0.0 mm |
| 修正後（先端 760.3・衝突形状は新） | **0 回** | 0.0 mm |

真ん中の行が「バグを入れたらテストが落ちる」ことの確認になっている。
接触しても机が動かないのは、シムの接触が水平方向に滑らかに解けるためで、
実機で縁に正面から当たる状況を再現しきれてはいない。
**シムは「当たったかどうか」までしか保証しない**——押す力の評価は
`scripts/fork_clearance.py` の 4.3N（机が滑り出す 21N に対して十分小さい）で行う。

### 質量表が形状を追っていなかった

すくい斜面を伸ばしたのに、質量表の櫛歯は `0.105 kg` の**固定値**のままだった。
形状から取り直すと **0.1106 kg**（+25g/本）。合計は 34.98 → **35.003 kg** で規定超過。

固定値は「一度計算したら形状を変えても追従しない」ので、
製作品は原則 `LEDGER.add_solid()`（体積×密度）で記録する。

超過ぶんは**櫛歯の幅 25 → 20mm** で解消した（−111g、合計 **34.89 kg**）。
布はもともと歯と歯の間（ピッチ 110mm）を渡っているので、支持点の幅を
5mm 狭めても山の保持性は変わらない。
上押さえ 25N を受けたときの歯のたわみは 1.5 → 1.9mm に増えるが、
このとき歯はまだ机の上にあるので荷重は天板が受ける。

## 33. 干渉チェックが素通りしていた — 「見ていないものは検出できない」その2

`scripts/validate.py`

§32 でフォークの最下点を測ろうとしたら、`_solids()` が **z = −2.0** を返した。実際は 761。

原因は build123d の構造で、**子ノードは親に付いた Location を自分の形状に持っていない**。
本設計では砲塔・グラバー・車輪・シンギュレータを
`Pos(...) * Rot(...) * link_xxx()` の形で**グループ単位に位置を与えている**ので、
葉をそのまま取り出すと局所座標になる。

| グループ | 修正前の葉 zmin | 正しい値 |
|---|---|---|
| base_link | 0.0 | 0.0 ✅ |
| slide_rails | 782.4 | 782.4 ✅ |
| turret | **−73.1** | 769.0 ❌ |
| grabber | **−2.0** | 761.0 ❌ |
| singulator | **−18.0** | 700.0 ❌ |
| wheel ×4 | **−50.0** | 0.0 ❌ |

干渉判定は bbox で粗ふるいしてからブーリアンを取る。
**片方が局所座標だと bbox が重ならないので、必ず「干渉なし」を返す。**
つまり砲塔・グラバー・車輪が絡む組み合わせは、**チェックが素通りしていた**。

§32 のフォーク衝突形状と全く同じ種類のバグである。

> **教訓**: 「チェックが通った」ことと「チェックが機能している」ことは別。
> 新しい検査を足したら、**わざと壊してその検査が落ちることを必ず確かめる**。

### 修正

`_solids()` で祖先の Location を掛け合わせてから葉を返すようにした。
単位 Location のとき（base_link 側の 167 個）は `moved()` を呼ばないので、コストも増えない。

なお `urdf/tr_urdf.py` は**問題ない**。あちらは `LINK_SHAPE` で
組み立て前の `link_xxx()` をそのまま使っており、URDF は各リンクの
慣性・形状を**リンク自身の座標系**で書くのが正しいため、局所座標のままでよい。

## 34. 干渉チェックが動き出したら、実機で組み立てられない箇所が5つ出た

§33 で座標バグを直した結果、干渉チェックが**初めて本当に機能した**。
その瞬間 **0 NG → 28 NG**。中身は寸法の詰めではなく、**そもそも組み立てられない**設計だった。

### 判定基準を先に直す（28 → 16）

28件のうち12件は**ボルトで留める取付面**だった。レールは上桁に、マストは後柱に、
椅子はフレームに固定するので、接触しているのが正しい。

「接触＝NG」の一律判定をやめ、**ペアごとに必要なすきま**を持たせた。

```python
("turret", "feed_ramp",       3.0),  # 旋回するので離す
("slide_rails", "grabber",    2.0),  # 摺動すきま
("slide_rails", "side_frame", 0.0),  # 取付面。**離れていたら NG**
```

`0.0` のペアは判定を反転させた。これで「取付面が浮いている」設計ミスも拾える。

### 本物の不良5件

| # | 不良 | 実機での結果 |
|---|---|---|
| A | ローラー駆動 M3508 が側面上桁を貫通（\|Y\|=408 vs 340〜360） | **組み立て不可能** |
| B | 斜路が砲塔台座を 27mm 突き抜け | **組み立て不可能** |
| C | 斜路が旋回体の掃引領域を通る | 旋回した瞬間に破損 |
| D | 固定側配線2本が旋回体の可動域を通る | 巻き込み・断線 |
| E | 斜路側板がキャリッジ横梁（Y=±313 全幅）を跨ぐ | グラバーが動かない |

### 共通する原因: 代表姿勢の座標を基準にしていた

5件すべてが「**ある1つの姿勢での座標**を見て逃げ量を決めていた」。

| 箇所 | 見ていた基準 | 見るべきだった基準 |
|---|---|---|
| 斜路 X1=175 | 漏斗の静止位置 125.6 | ヨー±30° の掃引包絡 |
| 同・修正後 X1=115 | **また静止位置** | 同上（掃引すると 94.1） |
| 砲塔系配線 Z=798 | 台座上面 838 | 仰角全域（ローラーが 758 まで降りる） |
| グラバー系配線 X=200 | 斜路の通路幅 \|Y\|≤320 | 旋回体の掃引（Z>760 では X=−27.5） |
| M3508 \|Y\|=330 | 軸端 310 | フレーム内側 340 まで 98.4mm 入らない |

元のコードのコメントは全部それらしかった。
`# 旋回体の漏斗手前で10mm縁切り` — 縁切りの相手が**動くこと**が抜けている。

**「〜の手前で N mm 逃がす」というコメントを見たら、その「〜」は動くかを確かめる。**

### 道具を2つ作った

数値を当てずっぽうで動かして**悪化させた**（側板 314→310 で 16→17 件）。
310 はキャリッジ(±313)と砲塔サイドプレート(±304.5)の**ちょうど間**で、
片方から逃げれば必ずもう片方に当たる位置だった。

そこで、決める前に見るための道具を作った。

| 道具 | 何を出すか |
|---|---|
| `scripts/slice_map.py` | 指定領域にある部品を \|Y\| の外側から全部並べる |
| `scripts/sweep_envelope.py` | ヨー×仰角を振ったときの**掃引包絡**（Z帯ごとの「固定物を置ける上限X」） |

掃引包絡の結果がこれで、以降のパラメータは**逆算で決まった**。

```
Z 700..760  旋回体の最小 X =  94.1  → 固定物は X <= 84
Z 760 以上  旋回体の最小 X = -27.5  → 置ける場所が無い
```

### 幾何で決まっていたこと

砲塔を細くして斜路を通せないかを計算したが、
斜路出口を X=115 に置くには**回転半径 ≤ 110mm** が必要だった。
射出ローラーは雑巾幅600に対応するため \|Y\|=285 まで要るので、
それを支える砲塔が半径110mmに収まることはあり得ない。

ヨー軸を前へ逃がす案も、旋回体の前端が **X=612** になり
競技中の外形規定 1200×1200（±600）を超えるため採れなかった。

**幅広の砲塔をヨー旋回させる以上、車体前半の上部（Z>760）は旋回体に明け渡すしかない。**
斜路は旋回体の下をくぐらせ、46mm 落として漏斗へ渡す構成にした。
落下は水平 0.30 m/s・落下 0.95 m/s で X 方向に 29mm 飛ぶが、
漏斗の受け幅 152mm に十分収まる。機構シムでも雑巾 10/10 枚が通った。

### 結果

**28 → 16 → 17 → 12 → 10 → 7 → 3 → 1 → 0 NG**（84項目）。
質量 34.82kg、外形 932×795×1155。

## 35. 板材のトポロジー最適化 — 「長方形から丸穴」をやめた

### なぜやめたか

`L.lighten()` と `L.lighten_path()` は、板の**外形を長方形のまま**にして中に円を並べる。
そのため

* 荷重が絶対に通らない**隅**が、外形の一部として必ず残る
  （`plate_audit` の使用率は yaw_side で 24%、pitch_side で 46〜52%。
  4 分の 3 は「そこに板がある」以外の理由を持たない材料だった）
* 円は等方なので、力の向きに沿った**方向性のある材料配置**ができない
* そもそも「どこを残すか」ではなく「どこに穴を開けるか」を決める問題なので、
  最適な形が探索空間に入っていない

以前のコメントには「SIMP にしない理由」として『板厚は製造制約で決まる／格子依存』
と書いてあったが、これは**外形を決めない**前提の話だった。外形まで決めるなら
SIMP でしか出せない形がある。格子依存は密度フィルタ（`rmin`）で切る。
フィルタ半径は「最小部材の半幅」という製造上の意味を持つ数字なので、
根拠をコメントに残せる。

### 何をしているか

| モジュール | 役割 |
|---|---|
| `src/topo/core.py` | 共通の型（`Region` / `TopoResult` / `Outline`）と格子マスク |
| `src/topo/simp.py` | Q4 平面応力 FEA + SIMP + OC 法。密度場を出す |
| `src/topo/shape.py` | 密度場 → 切り抜き輪郭 → build123d の面。製造制約の検査 |
| `src/topo/draw.py` | 荷重ヒートマップ・平面図・一覧の PNG |
| `scripts/topo_cache.py` | 組立から「板の幾何 + 固定宣言 + 投影外形」を JSON に落とす |
| `scripts/topo_opt.py` | 境界条件を宣言から組み、解いて、図と輪郭を出す |
| `scripts/topo_check.py` | 輪郭の鮮度・網羅・作れるかを毎回問い直す（`check_all` に登録） |

**境界条件は手で書かない。** `src/tr_fix.py` の固定宣言の**向き**をそのまま使う。

* 固定 … `FIXINGS[板]` に載っている相手（＝この板が留まっている先）
* 荷重 … `to=板` と宣言した相手。**その相手を通って降りてくる荷重**が力になる
* 座面 … ねじの当たり。密度 1 固定で消させない
* 逃げ … 板を貫通する相手（THRU / ROTATE / SLIDE / PRESS）。密度 0 固定で必ず抜く

### 引っかかった所（全部いちど間違えた）

⚠ **段数（`depth_of`）で固定と荷重を分けようとした。** 段数は固定連鎖の木での
深さで、枝分かれの向きとは別物。pitch_side が「支持ゼロの板」になった。

⚠ **「その板を抜いたら落ちるもの＝荷重」も駄目。** 構造は冗長で、yaw_side は
左右 2 枚で砲塔を支える。片方を抜いても落ちないので**荷重ゼロの板**になった。
`subtree_mass`（木で足し上げ）も駄目で、同じ形の yaw_arm_r / yaw_arm_f が
1N と 44N になった。葉から根へ流して親の数で等分すれば、経路が何本あっても
同じ答えになる（22N / 24N と対称になった）。

⚠ **貫通する相手を荷重から外していた。** 軸受は穴を通るので逃げ穴を作った時点で
処理を打ち切っていたが、射出ローラーはその軸受を介して側板にぶら下がっている。
pitch_side の荷重が全部 1N 以下（合計 12N）になり、ほとんど力の掛からない板として
解かれていた。軸受は穴の**縁**で力を伝えるので、穴のまわりの帯 4 本に載せる。
外接矩形 1 枚で載せると、穴の中の（密度 0 の要素に囲まれた）節点に力が載って発散する。

⚠ **拘束座と荷重座を「消させない領域」に入れ忘れた。** 境界条件を置いただけでは
SIMP はそこを削ってよいと判断する（力は節点に載るので材料が要らない）。
yaw_side_R の拘束座 2 か所が合わせて 912mm² 輪郭の外へ出た＝**相手に留められない板**。

⚠ **設計領域を外接矩形にすると、元が長方形でない板では改悪になる。**
ガセット（直角三角形）は矩形の半分しか肉が無いので、矩形全体を使ってよいことに
すると 62g → 105g と**重くなった**。板ソリッドを三角形分割して投影し、
元の外形の内側でしか材料を置けないようにする（元の肉抜き穴は埋める。
穴の位置ごと作り直すのが目的なので）。

⚠ **座面が細いと最小部材幅はそこで頭打ちになる。** 座面は密度 1 固定なので
フィルタが掛からない。rmin を 6 → 16.5 まで上げても 4.0mm のままだった。
効かないリトライは打ち切る。

⚠ **「元の板が細いなら下限を下げる」を入れて外した。** ガセットの元の外形は
最小幅 1.4mm と出るが、細いリブではなく**三角形の頂点**を拾っているだけ。
これを下限にすると何でも通る。形状の角と部材の細りは幅の測り方では区別できない。

### 扱えないもの（承知の上で使う）

* **平面応力（面内）だけ。** 水平な板（厚み軸が Z）は重力を面外曲げで受けるので、
  面内 SIMP にかけると「荷重ゼロ」と判定されてほぼ全部消える。対象から外して
  理由を出す（`--list` で見える）。面外曲げをやるには Kirchhoff 板要素が別に要る。
* **荷重は重力（動的倍率 3）と横加速度（1G）だけ。** 射出の反力、砲塔の慣性トルク、
  モーターの反力は入れていない。`plate_audit` / `fasteners` と荷重の考え方を
  揃えるため。ここだけ別にすると検査の間で食い違う。射出反力を入れるなら
  全部の検査で同時にやること。→ 射出系の板では**非保守側**になりうる。

## 36. 「ここは L 金具が入らない」は思い込みだった — 内隅を数える検査

### 症状

ビューアでマスト頭部を拡大すると、上部横梁（`mast_cross`）の端が主柱
（`post_rear_*`）の内面に**突き当たっているだけ**で、下から受けるものが
何も無い。バケツと水の鉛直荷重は全部この継手を通るのに、留めてあるのは
柱と横梁の ±X 面に貼った**平板（ジョイントプレート）2 枚**だけだった。

コードにはこう註釈してあった。

> ⚠ ここは L 金具が**入らない**継手。柱（X -285.4..-265.4）と横梁（同じ X
> 範囲）は X の幅が一致していて、横梁の端面が柱の内面を塞いでいる。
> 当てられる面は柱の ±X 面と横梁の ±X 面──**同一平面**なので L 字にならない。

前半は正しい。誤りは、当てられる面を **±X しか数えていない**こと。

### 原因 — 内隅の候補は 4 つある

T 継手（横材の端が縦材の側面に突き当たる）で L 金具が座れる内隅は、
**横材の側面 4 つ × 縦材の側面**で 4 通りある。使える条件は 1 つだけ:

> 縦材が、横材のその側面より**腕の長さ（17mm）以上はみ出している**こと

はみ出しが 0 なら 2 面は同一平面で、金具の腕は相手から外れて座面 0mm²
（`L.bracket_tee` の註にある「マスト 4 か所」がこれ）。数え直すとこうなる。

| 面 | 横梁の面 | 柱の面 | はみ出し | 判定 |
|---|---:|---:|---:|---|
| x+ | −265.4 | −265.4 | 0.0mm | 同一平面 |
| x− | −285.4 | −285.4 | 0.0mm | 同一平面 |
| z+ | 1172 | 1172（柱の上端） | 0.0mm | 同一平面 |
| **z−** | **1152** | **160（柱は床まで）** | **992mm** | **使える** |

**横梁の下面と柱の内面**。ここが本来の入隅で、しかも鉛直荷重の経路そのもの。
平板は ±X 面にあるので、鉛直せん断は溝ナットの摩擦とねじのせん断だけで
受けていた。L 金具なら横梁を**下から受けて**柱へ渡せる。

### 直した内容

* `brk_mast_corner_L/R`（HBLFSN5 相当・各 12g）を左右の内隅に追加。
  腕は横梁の下面（z 1146..1152）と柱の内面（|y| 334..340）、幅は X の
  20mm 帯にちょうど収まる。**両材への食い込み 0mm³**（当て面 340mm² ×2）。
  ねじは `bracket_screws` が腕ごとに 1 本ずつ、どちらも溝の中心へ入る。
* 平板は**残す**。X 方向のモーメント（前後の首振り）はそちらが受ける。
  金具と平板は稜線 1 本で触れるので `touch_ok` を宣言した。
* ⚠ **J8 のねじを M5×20 → M5×12 に縮めた。** 20 だと横梁の断面 20mm を
  ちょうど貫いて、先端が下面に届く。そこに金具の腕が来たので、
  ねじの先が座面を突いて金具を浮かせていた。長いねじは「余っても害は
  無い」ように見えるが、**反対側の面に何か付いた瞬間に害になる**。

### 検査 — `scripts/corner_bracket.py`

一度「入らない」と判断すると、その判断は図にも台帳にも残らないまま固定される。
判断のほうを毎回検査する。

    python scripts/corner_bracket.py [--md] [--code] [--only 名前]

押出材どうしの突き合わせ継手を実体の bbox から拾い（28 本・38 組）、
継手ごとに内隅の候補 4 つを上の条件で判定し、

* 使える内隅に金具（両材に留まると宣言された部品）が入っているか
* 入っていないなら、そこに `L.bracket()` を置いて他部品に当たらないか

を調べる。**合否は「使える内隅があるのに金具が 1 つも無い継手」だけ**で決める
（内隅が余っていること自体は不良ではない。軽荷重の T 継手は
`_butt_brackets` が片側 1 個と決めている）。`--code` を付けると、
置ける内隅について**そのまま貼れるコード**（`Pos(...) * Rot(...)` と
`put` / `bracket_screws`）を出す。

直す前に回すと、38 組のうち**マストの 2 組だけが「金具ゼロ」**として出た。
残り 36 組はすべて金具が入っていて、しかもこの検査は
「±X は同一平面」という元の註釈と同じ結論を独立に再現している
（＝人の判断が間違っていたのは 1 面ぶんだけ、という切り分けができる）。

### 結果（2026-08-01）

* 内隅検査 … 継手 38 組・**金具ゼロ 0 組**（直す前は 2 組）
* 組立（match・自動配置ねじを除く実体 590 部品）…
  浮き0 離れ0 未宣言接触0 食い込み0 座面不足0 工具入らず0
* 質量 … L 金具 12g ×2 で **+24g**。J8 のねじが 20→12 になったぶんは −数 g。

⚠ `out/screws.json` の自動配置ねじを入れると、金具の位置に溝ナットが
先に置かれている組が残る（`brk_mast_corner_* ↔ scr_a*` 4〜23mm³）。
ねじの位置は実体から決まるので、**`scripts/screw_place.py` を回し直せば
金具を避けた点に移る**。金具を足したら凍結を作り直すこと。

## 37. 「留まっている」と書いてあるだけで、ねじが 622 本描かれていなかった

### 症状

STEP をビューアで開いた人の第一声が「ボルトナットが全然ついていない」だった。
`scripts/fastener_bom.py` を回すと、そのとおりの数字が出る。

```
宣言 326 組 / 実体 148 本 / 未実体 622 本（220 組）
```

締結の宣言（`src/tr_fix.py` の `FIXINGS`）には `"4-M5 PCD35"` のような
note が付いていて、**買う数と質量はそこから見積もれていた**（員数表 1,574 個・
3,086g）。しかし図の上では 4 分の 3 の締結にねじの実体が無い。

これは見た目の問題ではない。**実体を置かないと言えないことが 3 つある。**

  * ねじの頭が座る面が本当にあるか（トポロジー最適化で外形を切った板は、
    「だいたいこの辺」に穴を開けると材料の外に出る）
  * 六角レンチが入るか（`assembly_check` の工具アクセス検査はねじの実体が
    無ければ何も見ない）
  * 相手を突き抜けて 3 つ目の部品に刺さっていないか

### なぜ 622 本を手で書けないか

宣言 1 つにつき「どの面の、どの座標に、どの向きで、何 mm のねじを」を
決める必要がある。手で書けば 622 × 4 つの数字で、しかも**相手を動かすたびに
全部書き直し**になる。板の外形はトポロジー最適化で決まるので、外形を切り直せば
ねじの位置も全部変わる。手書きの座標はその瞬間に嘘になる。

### やったこと — 位置を幾何から決めて凍結する

`scripts/screw_place.py` が、組んだ実体から置き場所を決める。

  1. 宣言された 2 部品の bbox から**接触の法線**を決める（3 軸とも試して、
     ねじを通せる点が最も多い向きを採る）
  2. 接触面上に 2mm 格子を張り、各点の**両側 0.4mm** が
     それぞれの実体の内部にあるかを `BRepClass3d_SolidClassifier` で見る。
     ⚠ **bbox の重なり矩形を使ってはいけない。** 外形を切った板は矩形と
     全く違う形なので、隅にねじを置くと空中に浮く
  3. 頭の座面ぶん（頭半径 + 1mm）だけ有効域を**収縮**し、残った点から
     互いに最も離れる点を貪欲に選ぶ（両端・四隅に散る）
  4. 相手の材が続いている深さを実測し、**長さと留め方**を決める
     （押出材 → 溝ナット / タップが立つ厚み → ねじ込み / 薄い → 貫通ナット）
  5. 軸の通り道・工具の入る空間・隣のねじとの当たりを見て、駄目なら次の候補へ
  6. それでも当たる相手は**宣言に出す**（貫くなら THRU、触れるなら TOUCH_OK）

結果は `out/screws.json` に**リンクローカル座標**で凍結する。組立側
（`tr_assembly.py` の `auto_screws()`）は読んで置くだけ。
**組立 → 位置計算 → 組立** の循環を断つのが凍結の目的で、`out/topo/` の
輪郭と同じ考え方。

⚠ **位置は全関節 0 の姿勢で測る。** 仰角が付いていると射出リンクの部品は
傾き、bbox（軸平行）が実体からずれて接触面が読めない。関節が 0 なら
どのリンクも並進だけなので、世界座標から引き算だけでリンクローカルに直せる。

## 38. 計測輪が 3 輪とも同じ向きだった — 横速度は「精度が悪い」のではなく出ない

### 症状

オドメトリ用の計測輪を 3 輪、`(210, 0)` と `(−350, ±350)` に置いていた。
どれも転がり方向は X。**3 輪とも同じ向き**だった。

### なぜ致命的か

1 輪が測れるのは「その輪の**転がり方向**の床速度」ただ 1 つ:

```
v_i = u_i · ( v + ω × r_i )
    = ux_i·vx + uy_i·vy + ( −ux_i·y_i + uy_i·x_i )·ω
```

未知数は (vx, vy, ω) の 3 つなので、3 輪あれば解ける — **ただし係数行列の
階数が 3 になる向きに置いたときだけ**。`u_i` が全部 (1,0) だと 2 列目が
全部 0 になり、階数は 2 にしかならない。

    | 1  0  0    |
    | 1  0  350  |     ← 2 列目が全部 0。det = 0
    | 1  0 −350  |

**vy は「精度が悪い」のではなく、式に現れない。** どれだけ良いエンコーダを
使っても出てこない。しかもこの機体はメカナムで、横行が主役の走り方をする。
落ちるのは**いちばん欲しい成分**だった。

### 直した内容

中央の 1 輪（`(210, 0)`）だけをヨー 90° 回して、転がり方向を Y にした。

    | 0  1  210  |
    | 1  0 −350  |     ← det = −700。階数 3
    | 1  0  350  |

⚠ **この節の「揺動アーム」「支点」は、いまの設計には無い**（→ §45 で
オムニ + リニアガイド + 輪ゴムに作り直した）。左右 2 輪の座標も
`(−180, ±345)` に変わっているが、**階数の議論はそのまま**成り立つ
（det = −690）。x が式に現れるのは 90° 輪だけで、そこは動かしていない。

* `_odo_unit()` に `yaw` を足した。**ローカル系で組んでから最後に回す**。
  座標を回した値で書き直すと、Y 方向の積み上げ表（`ODO_D_*`：タイヤ幅 →
  すきま → アーム板 → 軸受ボス → マグネット → 基板）との対応が読めなくなる。
* ⚠ 相手（押出材）は回らない。`F.face()` をそのまま使うと、90° 回した側で
  「留め代の幅」も「折る向き」も別の軸の値を読む。`hface()` を通して
  ローカルへ引き戻してから使う。
* 受けが変わる。腕が Y 方向へ出るので、支点は `(210, −100)` に移り、
  留まる先は横材 x=110 ではなく **x=210 の横材**（Y に通っている）になる。
* 支持側は −X（`si=+1`）。+X は前輪モーターマウント（X 235..365）が
  4mm まで迫っている。
* 留め代は相手の端でクリップするようにした。90° 回した輪では板が押出材の
  幅（20mm）の外に出るので、19mm 固定のままだと縁が宙に浮く。

### 使う側にも入れた

`control/tr_control.py` に `OdometryWheels` を足した。3 輪の周速度から
(vx, vy, ωz) をクラメルで解く（マイコンに載せるので numpy は使わない）。

⚠ **初期化で階数を実際に確かめている。** 配置を変えて向きが揃ったら、
走らせる前に `ValueError` で気づける。設計の意図をコードで縛るのは、
図の上のコメントより強い。

```
[0.3, -0.4, 0.7] -> [0.3, -0.4, 0.7]        # 真値から順→逆で一致
OdometryWheels(3 輪とも 0°) -> ValueError    # 揃った配置は弾かれる
```

## 39. アルミフレームの溝は 1 面に 1 条しかない — ねじが 84 本とも外れていた

### 症状

ビューアで骨格を拡大すると、押出材の面に**溝から外れた**ボルトが並んでいた。
面の端に寄っているもの、同じ面に幅方向へ 2 本並んでいるものまであった。

### 原因

`screw_place.py` は「接触面で**両方に材料がある**点」を格子で探して、
そこへねじを置いていた。押出材が相手でも同じ扱いだったので、

* **溝の真上は「材料が無い」と判定されて落ちる。** 溝の開口は深さ 1.9mm。
  表面から 0.4mm 探るやり方では、溝の上だけが候補から外れる。
  結果、**溝を避けた場所**にねじが並ぶ（下穴の無い肌に頭が乗っている）
* **幅方向に 2 列並ぶ。** HFS5-2020 の 1 面にある溝は **1 条**だけで、
  20mm 幅の面に 2 本は入らない。「面のどこでもよい」で散らすと必ず起きる

測ってみると、押出材に留まる 84 本が**全部** 1mm 以上ずれていて、最大は
6.0mm（＝面の端）だった。

### 直した内容

留める相手が押出材なら、置ける場所を**溝の中心線に拘束する**。

* 側面（法線 ≠ 長手軸）… 幅方向を面の中心へ固定し、**長手方向にだけ**並べる
* 端面（法線 = 長手軸）… 溝は無い。中心の下穴（φ4.3）1 つだけなので
  断面の 2 軸とも中心に固定する。側面を先に試す
* 押出材側の材料は**溝の底より深いところ**で見る（表面すぐを探ると
  溝の上だけが落ちる、という上の症状そのものになる）
* ⚠ **リベットは溝を使わない。** 面に下穴を開けるので、溝に縛ると
  「溝の空を狙って打つ」ことになる。実際それで、材まで届かない長さに
  なったリベット 27 本が押出材から浮いた。溝に縛るのは溝ナットだけ
* ⚠ **斜材には使えない。** 傾いた押出材は bbox が断面より太いので、
  bbox の中心線は溝の中心線ではない。判定できないものは従来どおりにする

### 工具の判定も直した（溝に縛ると当たり前に効いてくる）

溝の上にしか置けなくなると、「頭の外 18mm に工具が入るか」で落ちる組が
増えた。ここは 1 姿勢（関節 0）だけで見ていた。

⚠ **工具は「どこかの姿勢で入れば」入る。** 軸の通り道と違って、レンチが
要るのは組むときだけで、塞いでいるのが可動部ならどければよい。関節 0 と
装填の 2 姿勢で見るようにしたら、置ける本数が 307 → 333 に戻った。

### 結果

（溝に縛った直後の値。このあと姿勢と長さの判定を直して 339 本／104 組になる）

| | 前 | 後 |
|---|---:|---:|
| 押出材に留まるねじ（溝ナット） | 84 本 | 75 本 |
| うち溝の中心から 1mm 超ずれ | **84 本** | **0 本** |
| 置いたねじ（全体） | 345 本 | 333 本 |
| 全部を置けた締結 | 138 組 | 100 組 |

本数が減り、置けない組が増えたのは**制約が正しくなったから**で、退行では
ない。前は「溝の無い場所に留まっている」図だった。置けなかった組は
`fastener_bom` の未実体として残り、設計の指摘になる。

⚠ `scripts/screw_check.py` に**溝の上に乗っているか**の検査を足した
（D 項）。ここを見ていないと、次に置き方を変えたとき静かに戻る。

## 40. マスコットが 300×300×600 の箱だった — 規定 3.1.3 は「製作して座らせること」

### 症状

椅子の上に置いてあったのは `mascot_envelope`、つまり規定 3.1.3 の
**最小外形そのままの直方体**だった。周りの部品（上段 LiDAR・照準カメラ・
配線）はこの箱を避けて設計してあり、その点では役に立っていたが、

* 当日そこに置く**実物が無い**（作るまで誰も形を知らない）
* 「チームメンバーの一員とわかるような服を着せること」（3.1.3）を
  満たす面が決まらない
* 重心と固定点が出ない。競技中に落ちれば減点（3.1.3 最終項）

### デザイン — 流用しないことが規定の要件

規定は「著作権が絡むキャラクターは使用できない」と明記している。既存の
どれかに似せるのではなく、**この競技の要素だけ**で造形を組み立てた。

設定は「**絞った雑巾がそのまま生きものになった**」。

| 部位 | 由来 |
|---|---|
| 体に巻いた斜めのうねり 3 本 | 雑巾を絞ったときのねじれ |
| 頭のてっぺんの輪（Z=600） | 絞り終わりのねじり目 |
| 左右に張り出す耳 | 雑巾の四隅 |
| 目 | 縫い付けたボタン（糸穴 4-φ5） |
| 手 | 布のミトン。両手で雑巾を持っている |

服は掃除当番のつなぎと三角巾で、胸のゼッケンにチーム名を入れる。
動力・アクチュエーターは無い（3.1.3 で禁止）。電飾は付けていない。

### CAD としてどう作ったか

`L.mascot_parts()` が 9 部品を返す（つなぎ / 頭 / 三角巾 / 目 ×2 /
ゼッケン / 靴 ×2 / 持っている雑巾）。

⚠ **曲面に平らな板を当てても面では触れない。** ボタンや三角巾を Box や
Cylinder で作ると、頭とは点でしか接しないか、逆に深く埋まる。相手と
**同じ楕円体**を内面に持つ殻を切り出す `_patch()` を用意した。内面が
頭の外面そのものなので、隙間も食い込みも出ない。

⚠ **絞り目のうねりは「引く」のではなく「足す」。** 表面から数 mm だけ
彫るには「体を内側に縮めた形」が要る（オフセットは重く、失敗すると体が
輪切りになる）。巻き付けたねじれとして足せば体積が増えるだけで壊れない。

⚠ **ミトンは前腕の太さ（φ60）を包める高さにすること。** 44mm で作ったら
腕の下半分がミトンからはみ出し、下に置いた雑巾へ 8,886mm³ 食い込んだ。
「持っている」ではなく「腕が刺さっている」状態で、組立検査が拾った。

⚠ **曲面に付ける飾りは「繋がる」と「刺さらない」の幅が狭い。** 三角巾の
結び目と垂れで 2 回失敗した。

* 帯（頭の外へ 5mm）の高さでは楕円体が細っているので、頭の外面を基準に
  結び目を置くと帯から 9mm 離れる → **三角巾が 3 ソリッドに分断**
* 逆に内へ寄せると、垂れが頭の後ろの膨らみへ 19,803mm³ 刺さる

結び目は**帯の外面に食い込ませ**、垂れは**結び目の中心を通す**（頭には
寄せない）。この 2 つを守ると、頭との重なりは 15mm³ に収まる。
組立検査の「分断」と「食い込み」がそのまま効く。

外形は規定の **300×300×600 にちょうど内接**させた（「以上」が要件なので
ぴったりで満たす）。Y 方向 300 は両腕の外側、X 方向 300 は靴の先から尻、
Z 方向 600 は絞りのねじり目の頂点で出している。周りの部品の逃げは
箱だったときのままでよい。

### 質量と固定

体積 19.6L、EPP の芯（30kg/m³）＋フェルト張りで **1.2kg 前後**。
⚠ 規定の重量制限には**入らない**ので質量台帳には載せない（載せると
35kg 規定の集計が狂う）。ただし椅子マウントの荷重には効くので、
`scripts/fea_frame.py` は「椅子+マスコット 3.10kg」で見込んである。

固定は尻に埋めた M6 鬼目ナット 2 個 ＋ 座板の下から蝶ボルト。工具無しで
外せる＝規定「計量計測時には速やかに取り外せるようにしておくこと」。

`SEW`（縫い付け・接着）という固定方法を足した。⚠ WELD（一体成形）と
混ぜないこと。300mm³ まで重なってよい理由が「縫い代とフェルトの厚み」で、
溶接ビードとは別物。分けておかないと、どちらの許容を締めればよいか
後から分からなくなる。

## 41. 「まだ最適化していない板」は 24 枚ではなく 33 枚だった — 黙って落ちる経路が 3 つ

§35 で 9 枚をトポロジー最適化して、外した板は「理由つきで 24 枚」と書いた。
実際にはその表に**載っていない板**があり、しかも 3 つの経路で黙って落ちていた。

### 経路 1: 購入品の質量が 0 だった

`plate_audit` は部品の質量を「体積 × 密度」で出す。密度は `P.DENSITY`
（製作品の材料表）から引く。ところが LiDAR・カメラ・モーター・電池・基板・
ベルトは**外形だけ**を箱や円柱で描いてあり、その材質は材料表に無い。
`P.DENSITY.get(mat, 0.0)` は静かに 0 を返す。

結果、これらを支える板は「**荷重を渡す相手が宣言に無い**（この板は何も
支えていない）」と判定され、トポロジー最適化の対象から落ちていた。
落ちていたのは LiDAR ブラケット 3 枚・バケツ座・上押さえ板の 5 枚。

⚠ **板厚の検査（`plate_audit`）も同じ質量を使っている。** つまり
「モーターを吊っている板の板厚が足りるか」を、モーター 0kg で見ていた。

`ENVELOPE_RHO`（カタログ質量 ÷ 外形の体積）を `plate_audit` に足した。
`P.DENSITY` のほうへは入れない — あちらは `LEDGER.add_solid` が製作品の
質量を出す表で、購入品はカタログ値で別に計上している。混ぜると二重に載る。

ついでに、上押さえのスポンジに材質が付いていなかったことも出てきた
（材質不明の既定 A5052 で数えられ、40g のパッドが 1kg 超で板に載っていた）。

### 経路 2: 「載せてある」「貼ってある」は荷重ではない扱いだった

荷重を渡す締結の一覧（`STRUCT`）に `SIT` と `CLAMP` が無かった。
バケツ座はバケツ（10L）を `SIT` で、上押さえ板はスポンジを `CLAMP` で
受けている。**留め方が何であれ、上に乗っているなら荷重**である。

### 経路 3: 「板ではない」で消えていた

厚み 12mm 超・短辺 30mm 未満・投影 5,000mm² 未満は `continue` で捨てて
いた。理由も残らないので、`--list` の「外した板」にすら出ない。
分類して数えるようにした（下の一覧）。**「対象 9 枚」が全体の何割なのか
言えない状態**だったのが問題で、数字そのものより出すことに意味がある。

### 全部解いた結果（2026-08-02）

対象は 9 → 17 枚になった。**新しく入った 8 枚は 1 枚も採用していない。**
ただし理由は全部「解いてみた実測」に変わった。

| 板 | 結果 |
|---|---|
| bucket_seat | 384g（元 310g）。φ210 の逃げを与えた上でこれ＝元が既に荷重の形 |
| press_plate | 426g（元 374g）。設計領域（外接矩形）が元の外形より大きい |
| car_side_L | 連結成分 2 個のまま frac 0.95（設計領域の上限）で打ち切り |
| car_side_R | −1g。座面が板を横断していて削る余地が無い |
| lidar_high_brk | +5g だが最小部材幅 1.4mm。座面が 71% |
| lidar_low_brk ×2 | 座面 76% > 空き 64%。目標体積率が置けず**解けない** |
| disp_frame | +3g。座面 92%（PETG なので元から軽い） |

⚠ **`car_side` の「座面が 64% だから形では削れない」は解かずに書いた
見立てだった。** 結論は変わらなかったが、根拠が見立てのまま残るのは
`SKIP_PLATE` の趣旨（＝解いた上で割に合わなかったものだけ）に反する。
その注意書きを表の頭に足した。

### 見つかった副作用: 既存 9 枚を解き直すと太る

同じ設定で既存の 9 枚も解き直したら、4 枚が**前より重い解**になった
（yaw_arm_r 319 → 407g、pitch_side_R 194 → 345g など）。しかも致命的
不良ではないので、そのまま JSON が上書きされていた。

原因は境界条件が増えたこと。§37 でねじ 345 本を実体にしたので、
`yaw_arm_r` の座面は 3 → 27 個、逃げは 0 → 6 個になった。座面は

frac が 0.54 → 0.66 と自動で引き上げられる。

⚠ **板の形 → ねじの位置 → 座面 → 板の形** は循環している。ねじの位置は
いまの板の形から選んでいるので、前の輪郭でも座面は足りている
（`assembly_check` の座面不足 0 件）。**軽いほうを使えばよい。**

`topo_opt.py` に「前の輪郭より太い解では上書きしない」を入れた
（面積で比べる）。据え置いたことは指摘として画面に出る。
併せて、画面に出す指摘を**致命的なものから**にした。「使えない」と
言いながら、出ていたのは座面の角が 1mm² 欠けた話だけだった。

### 溝に縛ったら、姿勢と長さの詰めが甘いところが出てきた

置ける場所が「溝の上の線」だけになると、それまで面のどこかへ逃がして
いた分がそのまま制約になる。連続掃引（`sweep_fine`）が拾った 4 件は、
どれも**置くときには見えていなかった**ものだった。

* **姿勢を 2 つしか見ていなかった。** 関節 0 と装填はどちらもヨー 0 で、
  旋回そのものを見ていない。旋回プーリのねじが台座リングへ 135mm³
  食い込んでいた。ヨー ±30° を足して 4 姿勢にした
* ⚠ **足したのに効いていなかった。** 別姿勢へ移すのに位置を引き算して
  いたが、それが成り立つのは関節 0（並進だけ）のときだけで、旋回した
  姿勢では回転が入る。`_to_pose()` で Location を掛けて移す
* ⚠ その拍子に「方向に直交する 2 軸」を**成分が 0 の軸**で取っていた所が
  落ちた（斜めを向くと 0 の成分が無い）。外積で基底を作る（`_basis()`）
* **呼び長さへの切り上げで相手を突き抜けていた。** 掴み代 + かみ合いが
  17mm なら `screw_len` は 18mm を返す。ヨー 0 では当たらないので
  通り道の判定では見えず、旋回して初めて当たる。突き抜けるなら 1 段
  短い規格長へ落とす（かみ合い 1d は残す）

結果、行程の途中での食い込みは **4 件 → 1 件**（残るのはリベットの
かしめ側が台座梁に 46mm³。リベットは裏へ出るのが仕事なので、長さでは
詰められない）。置いた本数は 333 → **339 本**、全部置けた締結は
100 → **104 組**に増えた（工具の判定が姿勢を見るようになったぶん）。

## 42. 斜材のボルトが溝から外れていた — そして「ガセットは削れない」はその副作用だった

### 症状

ビューアで側面トラスの上端を拡大すると、斜材ガセット（直角三角形の板）に
**斜材の溝と合っていないボルト**が並んでいた。板側に穴も開いていない。

### 原因: 傾いた押出材の溝は bbox から出せない

§39 で「押出材に留めるねじは溝の中心線に載せる」を入れたとき、
`screw_place.ext_axes()` は長手軸を **bbox の辺の長さ**から決めていた。
斜めに寝た押出材は bbox が断面より太くなるので判定できず、`None` を返して
**従来どおり面に散らす**ようにしてあった。§39 の本文にもそう書いてある。
斜材は 2 本だけなので保留にしたつもりだったが、図には出ていた。

測ると、斜材に留まる 4 本は軸線から **3.0 / 3.7 / 5.5 / 6.1mm** 外れていた。
溝口は 6mm（軸線から ±3mm）なので、下穴の無い肌に頭が乗っている本数がある。
1 本は板の外（三角形の下 3.5mm）に浮いていた。

### 直した内容

**位置を自動配置から取り上げて、組立側で決める。** 斜材の軸線は組立が
持っている（`ax0`→`ax1`）ので、そこへ載せればよい。

* `tr_assembly._brace_bolt_holes()` … 斜材の実端から 15mm を 1 本目、
  斜辺までの残肉が「バカ穴の半径 + 4mm」を切る手前を 2 本目にする。
  検算で軸線からのずれ **0.000mm**、ピッチ 22.9 / 26.5mm
* 板側に φ5.5 のバカ穴を開ける（宣言だけで穴が無かった）
* 傾いた部材の芯は bbox から出せないので、**置いた側が `tr_fix.SLOT_AXIS`
  に出す**。`screw_check.py` に D2 項を足して、そこからの横ずれを検査する
* ⚠ D2 は **手で置いたねじも見る**。自動配置（`out/screws.json`）だけを
  見ていると、芯へ移したねじがまるごと検査の外に出る

### 「ガセットは削れない」は、この誤りの副作用だった

§35 でガセット 4 枚を「元が直角三角形。削れて +2〜3g で切り抜きの手間に
見合わない」と外していた。ボルトを直して解き直したら、そこから**さらに
4 つの誤り**が出てきた。どれも「削れない」という結論のほうを作っていた。

1. **相手の bbox を座面にしていた。** 斜材の bbox は 110×140 のガセットの
   60% を覆う。そこが密度 1 固定になれば、削る場所は残らない。
   荷重が板に入るのは**その相手を留めているねじの座面**なので、実体の
   ねじがあるならそちらに載せる（`topo_opt._screw_seats`）。
   ⚠ bbox が実体を表していないと**分かっている相手**（`SLOT_AXIS` に
   載っている斜材）だけに限る。相手が板の上に載っているなら bbox でよい
2. **座面の足し戻しが設計領域の外にも材料を置いていた。** ソルバは
   `core.dead_mask`（逃げ ∪ 領域の外）を見ているのに、輪郭を作る
   `shape.to_outline` だけが見ていなかった。密度場は三角形の中だけなのに
   輪郭は外接矩形の 88% まで戻り、**元より 79% 重い形**が出た
   （console は密度場から質量を出すので「−10g」と表示される。図を見て
   気づいた）
3. **形状の角を「細い部材」と読んでいた。** 直角三角形の鋭角の頂点は幅が
   0 に落ちる。`solve_auto` はそれを部材の細りと読んで rmin と frac を
   上限まで上げ、最後は「目標体積率が置けない」で落ちる（3 回とも空振り）。
   頂点は最適化で作った部材ではないので、**設計領域の段階で丸める**
   （`topo_opt._blunt`、直径 RIB_MIN の円が通るまで）
4. **板を貫くねじの逃げ穴を、ねじの実体の bbox で開けていた。**
   板を貫くのは軸（M5 ならバカ穴 φ5.5）で、溝ナットは相手の溝の中＝
   板の反対側にいる。bbox（φ11）で開けると穴が呼び径の 2 倍になり、
   縁の残肉 4.5mm が「最小部材幅 4.0mm。切れない」になる。
   ⚠ これは**穴を小さくしても直らない**（穴が原因だと気づけない）。
   `_parts.json` に呼び径を持たせて、ねじならバカ穴で抜く

## 43. 「発注できる状態」にする — 図が 1 枚も無かった、そして検査が偽の指摘を出していた

`BOM.md` には**部品名と数量しか無い**。STEP は 3 コンフィグまるごと 1 ファイル
（`out/tr_match.step`）で、部品 1 個を取り出す手段が無かった。つまり
「設計は終わっているが、加工屋にもプリンタにも渡すものが無い」状態だった。

### 出すもの（`scripts/export_fab.py`）

| 工程 | 出力 | 判定 |
|---|---|---|
| 切り抜き | `out/fab/dxf/<部品>.dxf` | **体積 ÷ 厚み = 投影面積**が成り立つ（＝その軸に一様な板） |
| 3Dプリント | `out/fab/stl/<部品>.stl` | 材質 PETG |
| 削り出し・曲げ | `out/fab/step/<部品>.step` | 上のどちらでもない |
| 購入・対象外 | — | 材質か名前で除外（理由を必ず書く） |

DXF はレイヤを **OUTLINE / HOLE** に分ける。1 レイヤに混ぜると、どれが外周で
どれが内側かを相手に判定させることになる。

⚠ **判定が付かないものを平板として出してはいけない。** 外形だけそれらしい DXF が
出ると、加工屋はそれを信じて切る。板厚を bbox の最小辺で決めるのも駄目で、
曲げ板や L 形は最小辺が板厚ではない。

⚠ **どちら側から見た図かを持ち回る。** 左右対称の対（`*_L` / `*_R`）を裏返しに
切ると鏡像の部品ができ、外形を見ても気づかない（穴の位置で初めて分かる）。

### 曲げ品は展開しない

最初「同じ板厚のスラブが 2 枚、直交して繋がっている」を面積と体積の式で
判定し、展開長まで出した。結果はこうだった:

```
roller_shaft_d  辺 1574.0 + 3.2 / 展開長 1573.8   ← 実物は φ12 の中空軸
press_guide_L   辺  513.2 + 3.0 / 展開長  512.8   ← 辺 3.0 は曲げではない
```

**部品の全長 602mm より長い辺**が出ている。逆に本当の曲げ板（`mount_brk_*` =
モーターマウント）は 1 枚も引っかからなかった。円筒の端面や小さな段差が
「もう 1 枚のスラブ」に化ける。

そして**展開長は本来こちらで決める値ではない**。内 R と K ファクタは曲げる機械
（V 幅・パンチ R）で決まる。推測した K の DXF を渡すのは、**穴の位置を間違えた
まま確定させる**ことになる（t4 で K が 0.1 違えば 0.6mm ずれる）。
→ 曲げ品には STEP を渡す。判定は `bend_hint()` の目安だけにした。

### 検査の 334 件は、大半が偽の指摘だった

`topo_check` が 13 枚とも NG・334 件を出していて、内容はほぼ全部
「ねじ座面が輪郭の外にはみ出している（致命的）」だった。**2 か所とも、
輪郭の側ではなく検査の側が間違っていた。**

**(a) 設計領域の外を数えていた。** 座面の矩形はねじの外接箱を
`SEAT_GROW`(=10mm) 広げたもので、板の縁の近くのねじでは**板の外まではみ出す**。
`gus_brace_L_lo` の 15.8mm² は「板の縁 x=−55 に対し座面が −56.75 まで伸びている
1.75mm × 9mm の帯」だった。板の外に材料は置けないので、これは
**どんな輪郭でも直らない指摘**。座面の**足し戻し**は最初から
`add.intersection(Polygon(reg.domain))` で設計領域を守っていて、
**検査だけが守っていなかった**。

**(b) わざと開けた穴を数えていた。** 輪郭は最後に `poly.difference(_voids(reg))`
で逃げ穴を開け直す（軸が通らなくなるので当然）。ところが検査は座面の生の矩形と
比べていたので、**穴の面積がそのまま「座面がはみ出している」として出ていた**。
`beltbrk_idl_R` の 23.8mm² は void[1] (r=2.8) の π·2.8² = 24.6mm² を矩形で
切った値そのもの。`yaw_side` の 15.9 / 12.3 / 8.4 も r=2.2 の円を縁で切った値。

→ どちらも `shape.check` で**座面を「設計領域 − 逃げ穴」で切ってから**
輪郭に入っているかを問うように直した。

### そして「解き直しても直らない」ループがあった

`topo_opt` には「前の輪郭より太い解では上書きしない」ガードがある（§42）。
そこに「前の輪郭がいまの境界条件で使えるか」という条件が無かったので、

1. 相手が動いて、前の輪郭では**ねじが留まらない**状態になる
2. 解き直すと（座面が増えているので）前より太い解が出る
3. 「太い」を理由に据え置かれ、**1 の状態のまま残る**

を繰り返していた。実際 8 枚の JSON が 8/1〜8/2 のまま止まっていた。

⚠ **据え置きの語（`UNUSABLE`）は、書き込みを止める語（`FATAL`）より広くする。**
`FATAL` に「ねじが留められない」を入れると、座面の角が丸めで 1mm² 欠けただけで
1 枚も書けなくなる。一方**据え置き**は「前の形で組立が成立している」が前提なので、
ねじが留まらない形を残す理由は無い。ここを 1 つの述語で兼ねていたのが原因。

### ついでに見つかった、発注そのものの穴

| 見つかったもの | 何が起きるか |
|---|---|
| `bom.py` が `HFS5-2020` しか拾っていなかった | **側面斜材 HFS5-2010 L707×2 が発注リストに 1 度も載っていない** |
| 廃止した砲塔横梁が `qty=0` で残り「長さ 0 / 0 本」の行になっていた | 買う相手に渡す表に、買わない行が出る |
| 手で書いた `M4×26` が 12 本 | 流通するのは 25 と 30。**棚に無い長さ**なので現場で置き換わり、図面と実機がずれる。しかも 26 だと斜材ガセット（Y 360..363）へ 0.25mm 刺さっていた → **12** に（掴み代 5.75 + ナット 3.2 + 座金 0.8） |

確認寸法・**同じ文書の中の矛盾**（「X ではない」と書いてある値が別の場所で
指示として使われていないか）・型番を見る。
`scripts/fastener_bom.py` には「流通する呼び長さに無い」判定を足した。

### フォークの下面に頭が出ていた（机の縁に当たる形だった）

`validate.py` の「フォーク実形状の最下点 759.30 vs 机上面 760」は、
**櫛歯を根元バーに留める丸頭ブラインドリベットの頭**だった。
`screw_place` は頭を薄いほうへ入れる（`head_a = ta <= tb`）ので、
櫛歯（t2.5）↔ 根元バー（22）では櫛歯側に座る。櫛歯が根元バーに触れているのは
上面なので、頭は**下面**に出る。760.5 − 1.2 = 759.30 で数字が完全に一致する。

歯の下面は「何も出てはいけない面」（出ると机の天板の縁に正面衝突＝規定 4.1.4a。
§32 でわざわざ下面を水平に保った面）。

→ **皿頭ブラインドリベット**（`RIVET_FLAT`、120°）を追加した。note に「皿」と
書けば `parse_note` が拾う。φ3 の頭は Ø6.0 / 高さ 0.87mm なので t2.5 の櫛歯に
沈む（残り 1.6mm）。**最下点は 760.5 ちょうどになった。**

⚠ 丸頭のまま「頭を上へ回す」では直らない。ブラインドリベットは反対側にも
膨らみが出るので、面一にするには座ぐりに沈めるしかない。

### 書き出しで詰まった 2 か所（同じ形の間違い）

**1. DXF が 1 枚も出なかった。** レイヤの色に `ColorIndex.WHITE` を渡していたが、
`build123d.exporters.ColorIndex` にあるのは 9 色だけで WHITE は無い。
しかも**分類の結果を rec に入れる前にファイルを書いていた**ので、書き出しが
1 行で落ちただけで板厚も面積も残らず、あとの板取り集計が `KeyError: 't'` で
落ちた。**分類とファイル書き出しは別のこと**として順序を入れ替えた。

**2. STEP が 9 部品で `RuntimeError: Failed to write STEP file`。**
組立から取り出したソリッドは `label` と木の親子（`topo_parent`）を Python 側の
属性で持っている。`export_step` はラベルの付いた形を**アセンブリとして**
書こうとし、子が無いので空の文書になって落ちる。切り分けの実測:

```
mount_brk_fl   label='mount_brk_fl'  raw=NG  nolabel=NG  solidwrap=OK  compound=OK
belt_clamp_L   label=''              raw=OK  nolabel=OK  solidwrap=OK  compound=OK
```

**ラベルを消すだけでは直らない**（属性ではなく木の側の問題）。
`Solid(sol.wrapped)` で裸のソリッドに作り直せば通る。TShape を共有するので
複製の費用も掛からない（`export_meshes._compound` が `Located()` を使うのと同じ理屈）。

### ねじと輪郭は不動点になる — 1 巡では収まらない

`screw_place` は**その時点の板の形**でねじを置き、`topo_opt` は**その時点の
ねじの座**で板の形を決める。だから 1 巡だけ回すと、

* ねじは古い輪郭の上に置かれている
* 新しい輪郭はそのねじの座を守って解かれる

という半端な状態になる。実際 1 巡目のあと `assembly_check` に
「`scr_a0231` が `ramp_strut_L` に接していない」が出た。
**`screw_place → topo_cache → topo_opt` をもう 1 巡**して収束させること。
`DESIGN.md` §10 の再生成手順は、この順序を 1 巡ぶんだけ書いてある。

⚠ トポロジー最適化した輪郭は矩形より頂点が多いので、**`sweep_fine` の実体計算が
目に見えて伸びる**（1 時間級）。`check_all` のタイムアウト 5400 秒はそのための値。

### 残 1 件の食い込みは「板の縁にリベットを打っていた」

`sweep_fine` がヨー 9.5° で `pedestal_beam0 ↔ scr_a0016` の食い込み 46mm³ を
出し続けている。実体を見ると **φ3.2 × 43mm のブラインドリベット**だった。
φ3.2 に 43mm は存在しない（掴み代の上限は 13mm 程度）。

なぜ 43 になるか。実測:

| 部品 | X | Y | Z |
|---|---|---|---|
| `brk_lift_L0` | 122.5..152.2 | **281.0..312.5** | 839..879.5 |
| `lift_guide` | 120.7..162.6 | **−281..281** | 839..901.4 |

**2 つは面ではなく Y=281 の「板の縁」で突き合っている**（重なり 0）。
だから `screw_place` が接触法線を Y に取り、リベット軸がガイド板の
**長手方向**（562mm）を向く。`depth_into` はそこに 30mm の材料を見つけ、
長さが 12（掴み代）+ 30 + 1 = 43 になる。t1.5 の板の縁にリベットは打てない。
その 43mm の尾が旋回すると台座横梁（Z 818..838）をかすめる。

**症状（46mm³ の食い込み）ではなく、原因（縁に留めている）を直すこと。**
受け金具をガイド板の**裏面へ 15mm ほどラップ**させ、面で留める。
コメントに書いてある「板の裏に沿う受け金具でその 31mm を渡す」の意図どおりの形。
⚠ ガイドは t1.5、受け金具は t4 なので、ラップさせるならガイドの法線方向へ
2.75mm ずらして裏面に載せること（そのまま伸ばすと板を食う）。
⚠ 受け金具は**仰角ユニットの掃引の外**に置く制約がある（仰角側板は仰角軸から
半径 161 の円を掃く）。Y を内側へ伸ばすときはそこを再確認する。

そして**この種の不良は「買えない締結具」として先に落ちるべき**だった。
`screw_place` はリベットの長さを実測の深さから決めていて、上限を持っていない。
掴み代の上限を入れて「リベットでは留まらない。ボルトか、面で重ねる形に」と
出すようにすれば、掃引の食い込みを追う前に原因の側で気づける。

## 44. バケツが「載っているだけ」だった — 規定 3.2.3 は固定を要求している

移動バケツの固定は、この設計でいちばん長く**形の無い**まま残っていた箇所だった。

```python
put(parts, ... * L.bucket(), "bucket", to="bucket_seat", how="SIT",
    note="固定バンド 2 本（規定 3.2.3 の位置決め）")
LEDGER.add("バケツ固定バンド/金具", 0.150, "概算", "マスト")
```

バンドは**図に無い**。質量台帳に 150g が載っているだけで、形も、ボルトも、
座も無い。しかも 3 つの検査が、それぞれ別の理由でここを見ないようにしていた。

| 検査 | 逃がし方 | 書いてあった理由 |
|---|---|---|
| `assembly_check` | `REST_OK["bucket"]` | 「競技で審判が置く（機体は掴まない）」 |
| `joint_load` | `SKIP_PAIR[("bucket","bucket_seat")]` | 「バンドで抱えるので座面の話ではない」 |
| `validate.envelope` | `skip=("bucket",)` | 「バケツの高さは規定から除く」 |

⚠ **3 つとも前提が違っていた。**

* バケツを置くのは審判ではなく**チーム**（規定 4.1.1「マスコットや移動バケツは
  ロボットを運び込む前までに設置を完了させること」）
* 規定 3.2.3a は「開口部を上方向に向け、競技中は常に**水平を維持できるように
  しっかりと固定**すること」。載せるだけでは規定を満たさない
* 除いてよいのは**バケツの高さ**であって（3.2.2 の脚注）、バケツを留める金具は
  機体。ところが `skip` は**パスの部分一致**だったので、名前に "bucket" を含む
  部品（受け板・押さえリング・位置決めタブ）が丸ごと外形から消えていた。
  受け板を厚くしてもタブを立てても「スタート時 高さ」が 1mm も動かない状態
  → 末尾一致（`/bucket/bucket` と `/bucket/bucket_2l_datum` だけ）に直した

### 規定の読み方 — どこまで加工してよいか

3.2.3c は**禁止の向きが片側だけ**である。

> c) ロボットとの固定は、バケツの 2L 目盛りよりも**下部**で行うこと。
>    **2L 目盛りより上部にはいかなる加工も施すことはできない。**

裏を返すと **2L 目盛りより下は加工してよい**。さらに

> d) バケツの固定**のみ**を目的とした部品以外をバケツの中に入れることは
>    認められない。

＝ 固定のための部品なら**中に入れてよい**。この 2 つを合わせると、
いちばん低い位置で完結する固定は「**底に穴をあけてボルトで留め、中で押さえ
リングを噛ませる**」になる。バンドで胴を抱く案は、締め付けが胴のテーパー
（片側 4.93°）を**上へ押す**方向に働くうえ、2L 目盛りとの余裕を高さで食う。

### いまの固定

```
        押さえリング PETG t4（バケツの中・規定 3.2.3d）  z=1177..1181
   ┌────────────────────────────┐
   │  ▼ M5 皿ボルト 4 本（頭はリングに沈む・PCD φ204）
   ├──── バケツ底 t2 ポリカ ─────┤                      z=1175..1177
   ├──── バケツ受け板 A5052 t3 ──┤                      z=1172..1175
   └──── 平座金 + ナット ────────┘
        位置決めタブ PETG 4 個（胴を 16mm 抱える）      z=1175..1191
```

* **皿ねじ**にしたのは、バケツの中が雑巾の落ちる面だから。頭が飛び出していると
  投げ込まれた雑巾が引っかかる。皿頭 M5 の沈み 2.5mm ＋ 残肉 1.5mm で t4。
* **押さえリング**は φ5.5 の穴 4 か所に集中する力を底の全周へ散らす。バケツの
  底は t2 のポリカで、座金だけだと縁から裂ける。
* **位置決めタブ**は胴のテーパーに沿った内面（すきま 0.3mm）を持ち、設置のとき
  バケツを落とし込むだけで底の穴が合う。走行中の横荷重もここで受けるので、
  ポリカにあけた穴が支圧で広がらない。

### 取っ手（規定 5.3「競技では取っ手を付けたまま使用し」）

バケツの吊り手は付けたまま使う。形は描いていない（購入品の付属で、カタログ
質量 978g に含まれる）が、**振れる範囲に機体を置かない**ことだけ確かめてある。
吊り手は縁の耳（r≈139）から鉛直に垂れるので、線は r 139..142、下端はバケツ底
から 90mm（z≈1265）。位置決めタブは r≤136 / z≤1191 なので、半径で 3mm、
高さで 74mm 外れている。

⚠ タブの高さ 16mm は**上下から挟まれている**。上は規定 3.2.2 のスタート時
1200mm（1175 + 16 = 1191。**これが機体の最高点**になる。前の最高点は 1179 で、
規定まで 9mm 残る）、
下は規定 3.2.3c の 2L 目盛り。⚠ **2L 目盛りの暫定値 65mm は高すぎる可能性が
高い。** 円錐台として体積を積むと 2L に達するのは底から 47mm 前後で、65mm では
2.8L 入る。買ったら実測して `BUCKET_2L_FROM_BOTTOM` を直すこと（16mm の固定なら
どちらでも通る）。

### 受け板 — 「板を決めてから丸穴で軽くする」をやめた

| | 前 | いま |
|---|---|---|
| 外形 | 340 × 340 の角板 | 受け円環（φ186/φ236）+ ビームに載る帯 2 本 |
| 肉抜き | φ44 を 58 ピッチで 12 個 | **無し**（形そのものが荷重の通り道） |
| 板厚 | t2 | t3 |
| 質量 | 309.5g | 296.8g |

φ44 の丸穴は中央 φ210 の抜きと重なって**三日月形の切れ端**を並べ、円環から
締結へ向かう荷重の通り道を横切って穴が開いていた。§35 で「長方形から丸穴」を
やめたのと同じ話が、この板にだけ残っていた。

形を決めているのは幾何のほうである。**受け円環の外径 236 と片持ちビームの
内面 |Y|=140 は 22mm しか離れていない**。四隅へ腕を伸ばす必要はなく、円環の
すぐ横から帯へ渡せばよい（前の板は四隅で留めていたので、腕が 100mm ずつ要った）。
入隅は R12 で丸める（shapely の closing で作るので、角の残らない連続輪郭になる）。

板厚を t2 → t3 に上げたのは、バケツが「載っている」から「留まっている」に
変わったため。板が沈むとバケツがそのまま傾く（3.2.3a の「常に水平」）。
受け円環の ±X 端は最寄りの桁から円弧で 90mm 離れていて、t2 では 3G で 1.1mm
沈む（t3 で 0.34mm）。**外形を切り直したので、厚くしても軽くなった。**

### 耳を「円」で出したら、タブの足の 44% が空中に出ていた

位置決めタブの座（耳）は、最初はリングから円をひとつ生やして作っていた。
ところが**円の耳は先へ行くほど細る**ので、タブの足（r=136 で幅 47mm の帯）の
両端が板からはみ出す。

```
tab   0deg  足 1206mm²  板の上  676mm²  はみ出し 530mm² (44%)
tab  90deg  足 1206mm²  板の上 1206mm²  はみ出し   0mm² ( 0%)
```

±Y のタブは円環と帯のあいだの材料に載るので 100%、±X だけが空中だった。
⚠ **上から見ても気づけない。** 耳もタブも同じ向きに並んでいて、足の角が
板の縁を数 mm 越えているだけなので、図では「載っている」ように見える。
`plate.intersection(足)` で**面積を数えて**出した。
→ 耳を矩形（radial 106..139 × 56 幅）に変え、タブの角度を 26° → 20° に詰めた。

### ついでに落ちた死重 — 片持ちビーム L410 → L300

受け板が 340 角から X 方向 190 の帯になったので、ビームの先端 110mm には
**何も載らない**。2 本で 110g の死重だった。帯の端（+25）に 10mm 足して 300 で
切る。⚠ ここは組立コードに `assert` を置いた（板の帯がビームからはみ出したら
その場で落ちる）。

## 45. 計測輪をオムニ + リニアガイド + 輪ゴムに替えた — 押し付けで誤魔化していたものが消えた

### もとの設計は 1 本の鎖でつながっていた

```
ウレタンの丸タイヤ φ50×W12
  → メカナムが横行するたび、計測輪は横へ引きずられる
    → 滑らせないために摩擦を稼ぐ           → 10.8N 押し付ける
      → 10.8N を出すために硬いばね（k=27N/mm）
        → 硬いばねを 2mm しか縮めずに済ませるため てこ比 0.20 の揺動アーム
```

先頭を**オムニホイール**に替えると、鎖はそこで切れる。横成分はローラーの
転がりで逃げるので、摩擦を稼ぐ必要そのものが消える。

しかも「10.8N 押せば滑らない」は、そもそも成り立っていなかった。
**タイヤの摩擦円は 1 つしかない**ので、横力に食われたぶんだけ転がり方向の
把持も失う。押し付けを強くすれば横滑りは減るが、横に滑った瞬間には
やはり転がり方向にも滑っていて、**エンコーダの読みはそのぶん嘘になる**。
オムニは縦と横の取り合いを起こさない。「転がり方向だけを測る」という
3 輪オドメトリの前提が、はじめて実機でも成立する。

### 必要な接地荷重は 10.8N → 7N に落ちた

摩擦が要らなくなったので、残る要求は 2 つだけ。

| 要求 | 必要な力 |
|---|---|
| ばね下（オムニ45 + キャリッジ40 + ブロック17 ≒ 0.13kg）が 5G で暴れても離れない | 6.4 N |
| LM ブロックのシール抵抗（0.2〜0.4N）を越えて路面に追従できる | 0.4 N |

7N を中央値に置いた。押し付けを落とせたぶん、転がり抵抗も床の消耗も減る。

### 揺動アームは、上下するたびに嘘の距離を足していた

腕で吊ると車輪は支点まわりの**円弧**を描く。腕長 145mm で上下 8mm 動くと、
接地点は水平に 145 − √(145² − 8²) = **0.22mm** ずれる。オドメトリはその
水平変位を「走ったぶん」として数える。目地を 1 回越えるたび 0.22mm、
3 分で 200 回越えれば 44mm の嘘が積む。しかも**行きと帰りで符号が同じ**
（上がるときも下がるときも支点へ寄る向き）なので、往復しても消えない。

直動ガイドなら車輪は真上にしか動かず、接地点の水平位置は動かない。
すべり軸受やブッシュ 2 個では代わりにならない — 片持ちの車輪から来る
モーメントでこじれて固着し、そのまま浮く（＝計測が止まる）。
**MGN9C を縦に 1 本**。ストローク ±8mm。

### 輪ゴムは「弱いばね」として素直

欲しいのは「ストロークの端から端まで押し付け力が変わらない」ことで、
ばね定数は**低いほどよい**。

| | 車輪まわりのばね定数 | ±8mm での荷重変化 |
|---|---|---|
| もと（k=27 コイル・てこ比 0.20） | 1.08 N/mm | 10.8 ± 8.6 N |
| いま（#10 輪ゴム 2 本・スパン 48mm） | 0.21 N/mm | 7.0 ± 1.7 N |

#10（折長 22mm）を 48mm に張ると伸び率 118%。天然ゴムの応力は
その伸びで 1.3MPa 前後、断面 1.1×1.1 のループ（2 条）で 1 本 3.2N。
**押し付け力は本数で合わせる**（1〜3 本で 4〜11N）。ゴムの弾性率は
ロットで ±30% 振れるので、実機ではばね秤で測って決める。

⚠ **輪ゴムは消耗品。** 紫外線と油で切れるし、張りっぱなしだと数日で
応力緩和して 2 割落ちる。工具なしで掛け外しできる φ4 のピンにして、
**試合ごとに掛け替える**前提にした。

⚠ **輪ゴムは押せないので、下端ストッパが要る。** もとの構成は
「ばね端末を座グリへ押し込んで引張にも効かせる」ことで、機体を持ち上げた
ときのアームの垂れを止めていた。輪ゴムはキャリッジを下へ引くだけなので、
何もしないとブロックがレール端から出て**ボールが落ちる**。輪ゴムの
固定側ピン座の上面（Z 50）をそのまま下端ストッパにした（部品は増えない）。

### 単列オムニは使えない

単列はローラーとローラーの谷で接地半径が落ちる。**転動径が計測の
スケールそのもの**（φ50 の円周 157.1mm ÷ 4096 カウント = 0.0384mm）
なので、転動径が周期的に変わることは、距離のスケールが波打つことと同じ。
双列を半ピッチ（18°）ずらして、片方の谷を相手の腹で埋める。

⚠ それでも包絡線のリップルは残る（実測で 0.2〜0.5%）。ただし**周期は
1 ローラーピッチ**で、1 回転（157mm）で均される。距離が伸びるほど相対
誤差は小さくなるので、系統誤差にはならない。系統ぶんは校正で吸収する。

### 3 つのつまずき

**1. ガイドを車輪の真上に立てると Z が足りない。**
車輪がいちばん上がった位置（+8mm）の頂点は Z 58、骨格の下面は Z 115。
残り 54mm に、ブロック 38.8 + ストローク ±8 + レール端の逃げ（片側 4〜5mm）
は入らない。→ **転がり方向の後ろへ 35mm 逃がす**。板が車輪の外周
（半径 25）を避けられるので下端を Z 40 まで下ろせ、レール 64mm が入る。

**2. MGN9C の「高さ 10」はレールを含む内数だった。**
ブロックが取付面から反対側へ張り出すのは 10 − 6.5 = **3.5mm** しかない。
10mm と読んでいたので、車輪外周との逃げが 6.5mm 甘く出ていた。
`odo_lm_block()` の原点を**レール断面の中心**に取り直した
（レールとブロックを同じ位置に置けば嵌まる）。

**3. 車輪幅 12 → 20 で、エンコーダがメカナムの中へ入った。**
支持側（内側片持ち）の積み上げがそっくり内側へ寄り、基板の背面が
|Y| 329.4 → **317** まで来た。そこはメカナム（|Y| 265.5..325 /
X ±250..350 / Z 0..100）の中。

* 外へ逃がす → スカート内面（|Y|=360）まで 5mm。無理
* 幅を削る → 単列に戻ることになる。無理

→ **車輪ごとメカナムの X 帯の外へ移した**（X −350 → −180、Y ±350 → ±345）。
⚠ 移してもオドメトリの式は 1 つも変わらない。転がり方向 +X の輪が測るのは
`v_i = vx − ω·y_i` で、**x_i は式に現れない**。効くのは 2 輪の Y 間隔だけで、
700 → 690mm（ω の分解能は 1.4% 悪くなるだけ）。x を使うのは 90° 傾けた
中央輪だけで、そちらは (210, 0) のまま動かしていない。
`control/tr_control.py` の `ODO_WHEELS` も同じ値に直した。
